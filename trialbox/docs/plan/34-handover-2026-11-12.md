## 2. How a card lands

1. One card, one branch `agent/<id>-<slug>`, one draft pull request, opened at once (the claim).
2. The test first, seen to fail; the failing output is in the pull request's body.
3. One adversarial review for every card that touches how a patient is excluded, who may act, what a restore or an
   erasure keeps, what the night publishes, or what a PRODUCTION box runs. The reviewer is a fresh subagent that has
   not seen the author's reasoning and must run throwaway tests, not only read. The brief is in section 4.
   On 2026-11-12 fifteen such reviews were run; every one found a defect the tests had not.
4. The lane fixes what the review found (tests that fail first) and writes the review and the fixes into the body.
5. When the fast tier is green on a head that holds master, the lane sends the integrator
   `train-ready: #<n> <full sha>` and pushes nothing more to that branch. A later push makes the pull request show
   closed instead of merged.
6. The integrator builds `train/<n>`: master (or the train before it) plus each head, `git merge --no-ff`. Conflicts
   in the files every lane appends to are resolved by keeping every side's lines. A conflict in code goes back to
   the lane that owns it; two cards of one lane that conflict are stacked by that lane.
7. The full suite runs once on the train. Green: merged with a merge commit (not squashed), so the card pull
   requests show as merged. Red: the failing tests name the card; it is dropped and the train rebuilt.
8. Nobody merges to master outside a train while a train is in CI: it sends the train round again.

Why trains: with one full run per card, each push started about 28 jobs and each merge sent the next card through
them again; with five sessions pushing, jobs queued for 40 minutes and more.

## 4. The adversarial review brief

Give the reviewer the pull request number, the card, the branch, the questions that would break this card, and:

> Adversarial review, READ-ONLY on the branch (no edits to it, no commits, pushes, PR comments, git stash,
> subagents). Synthetic data only; never read secrets. Work in a detached worktree of the PR's branch; throwaway
> tests under /tmp only (copy one into tests/ for a single run only if it must import helpers, then delete it);
> output of test runs to files; never pipe a test into tail inside an && chain. Read the diff against origin/master
> (or the PR it is stacked on), the PR body, the card's row and evidence, its decision record, and the owner
> decisions OD-10 to OD-21. Try to break the card: (1) the questions given; (2) was any existing test or assertion
> weakened, skipped or deleted, and can the new tests fail; (3) interrupt each new state change: killed mid-way,
> restarted, two at once, an exception in the middle; does it fail open; (4) old data: rows, files and backups
> written before this card, a box updated in place; (5) every other reader and writer of what changed (grep them):
> the paths the card forgot; (6) new stores in libs/tb_common/erasure.py and the record inventory; anything
> identifying or secret in audit, logs, process arguments or file names; (7) a new fixed limit that is neither
> derived nor a declared setting with a reason. Deliver at most 60 lines: verdict (merge / fix first / needs the
> owner's ruling); findings HIGH/MED/LOW each with file:line, a concrete sequence, CONFIRMED by running or by
> reading, and the smallest fix for each HIGH; then what held. State only what you verified.

Questions that found the most: which path does NOT go through the new single function; what a restart or a second
worker does half-way; what happens to rows written before the card; what the user is shown (a word on a page can be
wrong where the decision is right).
