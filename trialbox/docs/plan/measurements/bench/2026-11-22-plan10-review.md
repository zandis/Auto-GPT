# Bench measurements for the plan 10 review (2026-11-20 to 2026-11-22)

All runs on the bench host, driver 575 with CUDA 13 through the
forward-compatibility path. Public or synthetic data only. Install tested at dfb92007; tests at master 8085b053.
"Lost" = eligible patients the screen would drop (gate 5 limit: 5 %). "Caught" = ineligible patients excluded.

## 1. Accuracy: TREC CT N-12 (1,700 public pairs: 1,200 eligible, 500 not)

| Judge | Alone: lost | Alone: caught | With the shipped verifier: lost | caught |
|---|---|---|---|---|
| Shipped judge | 35.3 % | 71.8 % | **13.8 %** (CI 11.7-16.2) | 46.6 % |
| Shipped judge, `negation` prompt variant | 30.3 % | - | **12.8 %** | 47.0 % |
| candidate A (large open model) | 34.8 % | 73.2 % | **12.5 %** | - |
| candidate B | 33.8 % | 72.8 % | 13.1 % | 47.4 % |
| candidate C | 33.9 % | 67.2 % | 15.1 % | 47.0 % |
| candidate D | 35.8 % | 71.0 % | - | - |
| candidate E | 45.2 % | 78.0 % | 16.8 % | 48.2 % |
| candidate F | 46.8 % | 77.6 % | 15.9 % | 44.2 % |
| candidate G | invalid (no parseable answer, with and without reasoning) | | | |

Other variants: high reasoning effort gave no gain; the `suspected` variant was worse.

**Reading:** the shipped pair misses gate 5 by almost 3x (13.8 % vs 5 %). No open model tried fixes it (best
12.5 %). The gap is in the decision rule and the prompts, not model size. The bench reproduces the repository's own
figures for the pair.

## 2. Serving (the model server, one card)

| Setting | 1 user | 8 | 32 | 64 concurrent |
|---|---|---|---|---|
| `--enforce-eager` (as shipped), 32k | 29 tok/s | 225 | 879 | 1,682 |
| CUDA graphs on, 32k | 268 | 1,615 | 4,239 | **6,615** |
| `max-num-seqs 8` | 29 | 229 | 226 (21 s wait) | 225 (50 s wait) |
| `max-num-seqs 128` | 25 | 141 | 540 | 1,034 |
| n-gram speculative decoding | 187 | 1,002 | 2,861 | 4,225 |

- **CUDA graphs give 4-9x throughput with the same answers:** TREC lost 36.5 % eager vs 35.9 % graphs (CIs
  overlap fully; same judge, same 1,700 pairs).
- `max-num-seqs 8` queues everything beyond 8 parallel requests (21-50 s waits).
- Speculative decoding on random text: no gain over graphs. It needs a rerun on TrialBox-shaped text.

## 4. Languages

| Pipeline / model | en | zh-TW | ja | mixed |
|---|---|---|---|---|
| TrialBox, shipped judge: accuracy / wrongly blocked | 0.652 / 2.5 % | 0.661 / 2.0 % | 0.644 / 2.1 % | 0.638 / 2.3 % |
| TrialBox, shipped verifier | 0.497 / 1.3 % | 0.480 / 1.3 % | 0.471 / 1.6 % | 0.481 / 0.9 % |
| TrialGPT-style, shipped judge | 0.739 / 4.3 % | 0.723 / 3.6 % | 0.723 / 4.3 % | 0.743 / 4.2 % |
| TrialGPT-style, candidate A (large open model) | 0.724 / 11.2 % | 0.734 / 10.9 % | 0.719 / 12.3 % | 0.721 / 12.5 % |
| TrialGPT-style, candidate C | 0.736 / 7.1 % | 0.715 / 7.1 % | 0.734 / 7.0 % | 0.745 / 6.0 % |

(Criterion-level set, eval/criterion_ml, 1,000 criteria.)

- **TrialGPT-style prompting is more accurate (0.72-0.74 vs 0.64-0.66), but blocks 2-5x more eligible patients.**
  TrialBox's design trades accuracy for not wrongly excluding. That trade is real and should be stated.
- Accuracy barely differs by language at the criterion level. But the verifier's **evidence F1 in Japanese is
  0.336 vs 0.726 in English**: the Japanese evidence step is the weak point.
- Text keys (C4): of 3,389 English console keys, **301 ja/zh-TW texts differ in meaning** by two checkers of
  different families (175 ja, 126 zh-TW). Candidates, not verdicts: some are deliberate localisation.

## 6. Install test (lane J runbooks 01, 16, 05, 02, 06, 15)

41 findings (F-5 to F-45). The install works with workarounds. Main ones: F-18 (a stand-in model still needed),
F-20 (lake thread limit), F-32 (the nightly backup fails every night), F-33 (restore drill), F-36 (the
forward-compatibility driver path leaks driver memory per CUDA context, so cards stop after many starts),
F-41 (`eval qualify` could not find the pair of the bench layout, now fixed on master), F-43 (rehearsal refuses PRODUCTION),
F-44 (a failed nightly ingest leaves no reason), F-45 (the TrialGPT comparison scorer crashes on local output).

G1b (`tools/b200_qualify.sh`) does not run as written on a real box: compose runs from the bundle folder with no
`.env`; model-guard is never started; the default gateway URL is the orchestrator's port; `public_e2e` has no
SAE mailbox; neither `public_e2e` nor `goldens --check` writes the evidence `qualify.py` needs.

## 8. What this means for plan 10

1. **Gate 5 (lost < 5 %) is the core open problem.** Models will not close it. Next: a decision-rule sweep on the
   cached answers (vote of judge, verifier and a third model; abstain rules), and the `negation` prompt.
2. **Turn off `--enforce-eager`** in the serving profiles: 4-9x throughput, same accuracy.
3. **Japanese evidence extraction** needs work before a Japanese site (F1 0.34).
4. **The 32 GB tier cannot run the pair as is.** CPU only is about 11 s per criterion: fine for nights, not for
   the console.
5. **The 50,000-patient night is unproven** (F-44 first).
6. **CI:** fix or split the one slow console test, and the trains go green again.

Not done: medical question sets (download site unreachable from the host), Stage G (no candidate beats the pair),
B1 (waits for G1b inputs: N-12 score files and the MedTxt corpus).
