# The trec2023 run on paper, 2026-11-17 (card H-12)

**Reader:** the people who build TrialBox, and the integrator deciding whether and when to launch trec2023

This page plans one run of the public set trec2023 (TREC Clinical Trials 2023, 500 pairs) on the GPU VM, with three
protocols in flight. Nothing was launched. No cloud call, model, GPU or download of set data was made. The page was
written on master `fae5c1f774a668d913bb1fcd95b714a42d6dfe94`. Every command quoted below was run there, and its

## 1. The plan

### The launch line

The driver is `deploy/gcp/box-run.sh`. The form is the hand-over's section 4.8, with the D7 default of three in
flight written out. The owner's yes comes first: this line starts a paid VM.

```
python -m tools.box_run src-bundle --commit <full sha> --out /tmp/src.bundle
deploy/gcp/box-run.sh --preflight <the options below>          # free; exit 0 first
deploy/gcp/box-run.sh --mode validation --steps dev,acc --release-id dev-<commit12> --commit <full sha> \
    --src-bundle /tmp/src.bundle --only trec2023 --acc-rs-tag <new tag> --acc-streams "trec2023:3" \
    --acc-deadline "trec2023:23400" --acc-min-start 600 --skip 08-qualify --no-wait
```

| Option | Value | Why |
| --- | --- | --- |
| `--steps dev,acc` | images built from the commit, the stack, G-1, the canary, then the set | as the evidence columns since L7 |
| `--only trec2023` | the set at its plan size, 500 pairs | `tools/public_accuracy/plan.py` RUN_A |
| `--acc-rs-tag` | a tag not used before on this VM, at most 4 characters | see "The protocol ids" |
| `--acc-streams "trec2023:3"` | 3 in flight | the default for a compile-bound set (D7); the most TB_WORKERS 4 allows |
| `--acc-deadline "trec2023:23400"` | 6.5 hours | the set must end inside the launch's 8-hour cap; see "The deadline" |
| `--acc-min-start 600` | the default, written out | D4: no protocol starts with less than 600 s of the budget left |
| `--skip 08-qualify` | qualify left out, and said | as section 4.8; qualify is not this run's question |
| `--acc-protocols` | **not passed** | see "The protocol ids" |
| `--site-env` | not passed | trap T20: the embed limit is master's default unless set |

Run 07g (the canary through the box's gate) before SCREEN, as trap T22 says. Without it, `note_block` stays off.

### The protocol ids

The free listing, run here:

```
$ PYTHONPATH=libs:services:. .venv/bin/python -m tools.box_run acc-ids --only trec2023 --rs-tag t1
{
 "rs_tag": "t1",
 "sets": {
  "trec2023": {
   "prefix": "Ut1",
   "ids": null,
   "how": "not known here: the sample is drawn from the set's source files, not in the local cache"
  }
 },
 "refused": []
}
exit 0
```

- **The ids are not known before the VM builds the set.** The set's source files are not in this checkout's cache, so
  no filter can be checked here.
- **A wrong filter would still pass here.** Asked with a made-up id, the listing matched it, because only the prefix
  is checked when the ids are unknown:

  ```
  $ ... acc-ids --only trec2023 --rs-tag t1 --protocols "trec2023:Ut1NCT00000000"
     "matches": ["Ut1NCT00000000"]   "refused": []   exit 0
  ```

  On the VM, `box_vm.py acc-set` refuses an id the set lacks, and that is a STOP after the install has been paid.
  So **no `--acc-protocols` filter should be passed.**
- **The tag's length.** An id is the prefix `U`, the tag and the NCT id. Ids are at most 16 characters
  (`tools/public_accuracy/site.py` RULESET_ID), and an NCT id has 11. With a tag of 5 or more characters, every id
  falls back to a number (`U<tag>PA0001`). Keep the tag to 4 characters or fewer.
- **Tags used before:** `2` and `m2` (hand-over section 4.8; P1b). A second compile under an id the box has already
  approved fails (trap T3), so take a new tag.

### The deadline and the cap

- **The cap.** The driver's estimate gives this launch 8 hours: dev 3 and acc 5. The acc cap is the plan's high bound
  of 11,556 s x 1.3, rounded up. The VM powers itself off at `tb-max-minutes` = 8 x 60 - 5 = 475 minutes.
- **The deadline.** Without `--acc-deadline`, the set's budget is 1.5 x 11,556 s x 4 = 69,336 s (section 8: the
  slowdown is 4 until a whole set has measured it). That is longer than the cap, so the cap would end the set.
- **What the line gives.** `trec2023:23400` keeps the set inside the cap:
  - 8 h less 5 minutes;
  - less at most 0.99 h of fixed steps (section 2);
  - less about a quarter of an hour, not measured, for the set's end: audit, traces, pack and upload.
- **At the lower rate** the set ends in about 3.1 hours (section 2).
- **At the higher rate** about 205 of the 297 protocols are attempted (23,400 / 114.3). The rest are cut.

### What a budget cut leaves, and what a resume picks up

Read in `deploy/gcp/box_vm.py` and `deploy/gcp/box-install-run.sh`. None of this was run.

- **A protocol cut by the set's budget** is `not_run_time_budget`. It is not a failure, and it is not attempted
  (H-3's scorer). A later attempt **on the same work folder**, with time left, takes it up again and waits for the
  jobs it had started (D4).
- **A set that ends by its own budget** ends its step as `done`. A plain `--resume` keeps a done step ("finished
  before; not run again", `run_step`), so it does **not** pick the cut protocols up.
  - `--redo 60-acc-trec2023` runs the step again from no work. The earlier work goes to
    `logs/60-acc-trec2023.work-<retry>`.
  - Approved protocols reuse their approval (F29). Protocols already screened are screened again.
  - `acc-score` scores one work folder. Nothing in the repository merges two attempts' answers.
- **A set stopped mid-step** (a pre-emption, the VM's cap or the cloud's cap) is not ended. `--resume <run id>` runs
  `60-acc-trec2023` again on the same work: finished protocols are kept and started jobs are waited for. The set's
  clock counts the earlier boots (`set-clock.json`). Give `--acc-deadline` again on the resume, since it holds for
  one launch only (trap T19). The set is the launch's first, so it takes step number 60.
- **The choice for the integrator.**
  - A budget inside the cap: the line above. The run ends cleanly, and whatever is left is a separate decision.
  - A budget above the cap, for example `trec2023:36000`: the cap cuts the VM, and one `--resume` with the same
    budget finishes the set. That costs one more boot.

### What is scored afterwards

`box-run.sh --collect <run id>` fetches `acc/trec2023.tgz` and scores it outside the box (`tools.box_run acc-score`,
which calls `tools/public_accuracy/score.py`). For trec2023:

- **Protocols** (H-3, D-1107):
  - screened, cut by the budget, failed before SCREEN, failed in SCREEN, each failure by class;
  - the failure share with its exact 95 % interval;
  - the named boolean "fewer than one protocol in ten failed".
- **Pairs:** for each of the 500 NIST-labelled pairs (eligible or excluded), the box's answer (excluded, listed,
  open or unanswered). Reported as eligible lost, excluded caught, wrong exclusions, unanswered and open. A pair on
  a protocol that never screened is counted by that protocol's status. There is no S1 conflict count here: trec2023
  has no criterion labels.
- **Written lines** (S3, S4): the age and sex lines the builder placed, from `gold/written.json`.
- **Compiled:** protocols, criteria and the class split.
- **The answer key:** each score names its key. Key v2 is current (`tools/public_accuracy/key.py`).

The offline replay (`python -m tools.public_accuracy.replay`, D-1111) can then score the stored set at level (a).
Level (b) re-runs the parts that need no model, from the run's stored replies (section 4).

### Findings

1. **No pin for the trials' criteria.** trec2023's protocols are ClinicalTrials.gov's current record, not the
   snapshot NIST judged (`sets.read_trec`: "criteria from ClinicalTrials.gov's current record, not the judged
   snapshot").

   - A trial whose record now has no criteria drops out of the pairs, so the 297 and 500 can move.

2. **Key v2 has no sha256 for any set yet.** `eval/public_accuracy_key/MANIFEST.json` pins key v1's sigir and jmed

3. **The register row for live records says more than the code does.** `pubacc-ctgov-live`'s evidence column says

4. **NIST's terms are still "permission-to-ask".** NIST states no terms. The run is internal validation, which the

## 5. Risks, and the recommendation

### Risks

- **The rate on master is unknown.** The only trec2023 figure is from `1157c9bf`, with one in flight and 63 % of the
  started protocols failing. If master's protocols mostly reach SCREEN and SCREEN is the slow part, the high figure is
  low.
- **Three in flight is untried.** A gain below three times one in flight moves the result toward the high figure.
- **Old labels on current texts** (finding 1). A wrong exclusion on a trial whose text changed since 2023 is not
  necessarily the box's fault. The scorer cannot tell.
- **The rest of a budget cut is awkward to finish.** A set ended by its own budget needs `--redo`, which screens
  again what was done. The alternative is a cap-cut and a resume, which costs a boot.
- **Spot.** A pre-emption costs a boot and a resume (trap T13).
- **The money.** The high case is a third of what is left, before the confirming launch.

### What would make it not worth its cost

- It is launched before the confirming launch, so it measures code whose sigir failure share is not yet confirmed.
- No one has decided how wrong exclusions on drifted trial texts will be read.
- At the high rate, the running total would pass the part B stop (US$130), if that stop still holds.

### Recommendation

**Run it after the confirming launch, not before.** The confirming launch runs sigir (103 protocols) on master with
three in flight. That measures the two figures this estimate lacks: the rate at three in flight, and master's rate
for a compile-bound set. It also tests the targets of plan 42 section 3. With sigir's rate on master:

- the trec2023 estimate becomes one figure instead of a 3.7 to 10.7 hour range;
- the deadline can be set so that all 297 protocols fit one cap, or the cap-and-resume route chosen on purpose.
