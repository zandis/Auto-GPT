# R1-P2: the time per chart, how the walk measures it (lane DB, 2026-11-24)

*Card R1-P2, step S2, the owner's ruling of 2026-11-23 on #639. This page says what is measured and gives the walk's
commands for the B200 at 600 and at 5,000 synthetic patients. It holds no result yet: the walk posts its numbers on
#639. Every patient is synthetic.*

## What is measured, and from where

| Part | Source | Per chart or per run |
| --- | --- | --- |
| Ingest and mapping | the ingest job's seconds and patients (`--ingest-seconds`, `--ingest-patients`) | per chart (ms) |
| Each bulk stage: S0, S1 (coded rules), S2, S2b (note retrieval), sample, S3, S4, tiers, S5, writes | the job file `cascade_timing_<study>_v<version>.json`, published while the flag `screen.timing` is on | seconds per stage and per 1,000 charts |
| Each model call: role, stage, the caller's time, tokens in and out | `llm.call` in the audit (`asking`, H-16) | per chart: median, p95, max |
| The server's time and the wait for a slot | `llm.gateway.call` (`latency_ms`, `slot_wait_ms`), joined by `call_id` | per chart |
| Queue, prefill, decode, first token, end to end | each model server's `/metrics` before and after | per server: seconds and mean per request |
| The cards and the CPU | `nvidia-smi` (`gpu.csv`) and `/proc/stat` (`cpu.csv`) every 10 s | per run: mean and peak |
| Throughput | the run's wall seconds over the charts in scope | seconds per chart, charts per hour |
| The share of charts that reach the models | the charts with a model call over S0's patients | per run |

A chart's **model time** is the sum of its own calls, which overlap when calls run side by side. The **throughput**
is what a chart costs the run. Both are reported; neither stands for the other.

Not measured by this card: the time of each SQL query inside S1 (S1's total is), and the time inside the embedder
(S2b's total is). Prefill and decode come from the server's counters only where the server reports them; a server
without them is named in the report (`not_reported_by_server`), never estimated.

## The walk's commands

On the walk box, from the repository checkout (`.venv`), for each size (600, then 5,000):

1. On `/ops/flags`, set `screen.timing` to `on` with the reason "R1-P2 measured run, <size> patients".
2. Start the sampling, with the two model servers' `/v1` addresses and the root-only file that holds their key:

   ```
   python -m tools.chart_times watch --folder <results>/r1p2/<size> \
       --server judge=<judge /v1> --server verifier=<verifier /v1> --key-file <root-only key file> &
   ```

3. Note the time, then start the screening on the console ("screen now", the whole hospital) and wait for it to
   finish.
4. Stop the sampling: `touch <results>/r1p2/<size>/stop`. It writes `watch.json`.
5. Download the job file `cascade_timing_<study>_v<version>.json` from the job's outputs.
6. Make the report from a copy of the audit folder (the services' `/data/audit`):

   ```
   python -m tools.chart_times report --audit-dir <audit copy> --folder <results>/r1p2/<size> \
       --timing <cascade_timing file> --since <the time noted in step 3> \
       --ingest-seconds <ingest seconds> --ingest-patients <size> --out <results>/r1p2/<size>/report.json
   ```

7. On `/ops/flags`, set `screen.timing` back to `off`.

The report holds counts, times and percentiles only, no pseudonym, so it may be posted with the walk's logs. Run the
same at concurrency 16, 64, 128 and 256 (`TB_SCREEN_LLM_CONCURRENCY` and the servers' `--max-num-seqs`) for the
serving setting per profile, and with each precision (BF16, FP8 and today's 4-bit) for the precision comparison.
