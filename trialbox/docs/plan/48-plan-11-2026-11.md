## 1. For the owner

### 1.1 Ring 1 in one paragraph

Ring 1 is the MVP: what ring 0 promised, run in full by a hospital person from the release bundle, plus the two first
sites' data doors on synthetic stand-ins, every code system loaded at install, the clinical database design, Medplum
as the FHIR store, the EDC, every hardware profile and Windows, a measured comparison with every public Lind figure,
and the whole test set green three times in a row. It is built in nine steps. Each is walked on the B200 from a fresh
bundle, with every earlier step walked again. Real patient data is never used to prove it. At CGMH and 医誠会, real
data is read only on the hospital's own machine, and only counts leave (section 7).

## 3. Ring 1: does, does not, proved by

### 3.1 Does

Everything ring 0's page in D-1070 says it does, done by a hospital person on a box installed from the release bundle,
with no step done by hand behind the scenes, including install, update, the night, the review, audit, backup and a
live restore [#639 7107908330]. And:

1. **Installs first, asks after.** Four questions before the install (language, time zone, the first administrator,
   the key passphrase without a TPM), at most 11 while it runs (U-5, the cut of 57 to 11 [#639 7107930549]). A
   PRODUCTION box refuses by name, until filled in: opening a study for real patients, an SAE notice and the first
   real night.
2. **Loads every code system at install from one manifest** and updates it later: ICD-10-CM, WHO ICD-10, LOINC, ATC,
   SNOMED CT, UMLS, NHI order codes, JJ1017, departments, lane M's tables, each with name, version and hash, in all
   three readers (the compiler's folder, the OMOP vocabulary, the FHIR store). Licensed systems come from the
   hospital's own copy and never reach a backup (V-18, DB-C1 [#639 7105754899, 7107896921]).
3. **Stores and searches by the clinical database design**: one manifest, value-set hits per snapshot, composite
   indexes, slice-restricted queries, versioned note facts, date intervals, a hospital-wide patient profile and a
   measured vector search (DB-C1 to DB-C10).
4. **Reads both sites' sources** on synthetic stand-ins shaped like them: CGRD-type views and SSI-shaped SS-MIX2
   (section 2.1), with delta nights.
5. **Reads notes as written inside the box and masks wherever data leaves it** (D-1093, MASK-1).
6. **Runs on Medplum** as its FHIR store, with the same nights' results as on HAPI.
7. **Works with the EDC**: forms, pre-fill from the box, write-back after a person confirms, audit (section 8).
8. **Measures itself against every public Lind figure** by the same definition (section 10).
9. **Runs on every profile** (32, 48, 96 and 128 GB) and on Windows.
10. **Is green three times in a row**: the whole test set, back to back, on one master commit.
11. **Repeats itself**: two runs of one night on one snapshot move no patient between tiers (E2-9 [#639 7107834329]).
12. **Speaks the site's language**: en, zh-TW and ja, the core terms read by native readers (9k-16).

### 3.2 Does not

- No real patient data in any proof; no real data anywhere but the hospital's own machine (section 7).
- No third site, no multicentre run, no study package between sites, no coordinating view (ring 3).
- No second data door at a site: no DPC, receipts, cancer registry, SSI database door (10B-20), REDCap as a read
  source, or FHIR bulk door (ring 4).
- No claim the hospital can run it without TrialBox (ring 2), no accuracy bound (ring 2). The outside penetration test
  is before each site's first real-data run (R1-P1).
- No customisation beyond built flags, no reimbursement or registry triggers (ring 4).
- No REDCap source, SQL or text in this repository; what must live elsewhere goes in the owner's private EDC
  repository [#639 7108012824].

### 3.3 Proved by

Ring 1 is proved only when each of S0 to S8 is walked on the B200 from a fresh release bundle, every line passes, each
walk repeats all earlier steps, and the walk's lines are on #639 with their logs [#639 7108087457]. Nothing counts as
done on CI or a lane's container alone. Every function is installed by a hospital person, runs, and is validated:
measured against its stated figure on public or synthetic sets, with the evidence filed under `docs/validation/`
[#639 7108012824].

**R1-N1: screening on demand; the scheduled run for bulk work only** [#639 7116081173, the owner's ruling].
Screening is not tied to the night: a person starts it at any time, for one study or for all. The scheduled run does
only bulk work, and only when there is work:

1. a full re-ingest or back-fill;
2. the model reading notes to fill structured fields (facts found in notes, stored with their quote and version,
   DB-C7);
3. re-embedding after an embedder change;
4. re-screening every open study after a ruleset or code-system update.

The card: the console's "screen now" runs one study on demand and shows the time it is expected to take, from the
speed line below; the scheduler starts the four bulk jobs only when one has work; and "night" becomes "run" wherever a
person reads it (console, mails, reports, runbook pages a site reads). Size M. Lane: the integrator's choice (the
scheduler is lane DB's and lane U's to read).

4. **Audit**: one audit event per step on the box's chain, refusals included, and the EDC's own audit row for each
   write, linked by id.

### 10.0 One metric: Lind's, on our whole system (card R1-L0, the first card of S6)

Lind's peer-reviewed figure, 94.2 %, is **whole-system, per-criterion agreement with experts, coded and note criteria
together**: the system's answer for each (patient, criterion) against expert coordinators' adjudication. Ours must be
measured the same way: **the whole system** (the coded rules and the model pair together, with D-1069's routing), **on
the product path** (the installed box's SCREEN, from the release bundle), **per (patient, criterion)**.

**The label mapping, written first.** The journal paper was refused to this reader, so its exact label set is not yet
read; R1-L0's first task is to read it and amend this table before any run.

| The box's answer for a (patient, criterion) | Mapped label |
| --- | --- |
| A coded rule decides "met" (an inclusion holds, or an exclusion's condition is present) | met |
| A coded rule decides "not met" | not met |
| The model pair agrees "met", with a quote | met |
| The model pair agrees "not met", with a quote | not met |
| Unknown; data missing; a single model; the pair disagrees; a negated, family or suspected quote (D-1069); a quoteless note answer; any answer sent to review | not determinable |

Gold labels are met, not met or not determinable. **Agreement** is the share of (patient, criterion) pairs whose mapped
label equals the gold label, over all pairs. A "not determinable" answer against a met or not-met gold counts as a
disagreement. If the paper's set has only met and not met, "not determinable" is still a disagreement against either.
Reported overall, coded criteria alone and note criteria alone, per language, each with its count of pairs. Reported
with it, never instead of it: the decided share, the false-block rate (gold met for an inclusion, or gold
absent for an exclusion, answered so that the patient would be excluded), and the split by criterion kind (coded,
note) and by language.
