## 1. Purpose and scope

This plan states how TrialBox is shown fit for its intended use (TB-PLAN-05 §1.2) at each pilot site before real patients are screened, and how it stays fit afterwards. It covers the software TrialBox ships (GAMP 5 category 5), the configured products it runs on (category 3 and 4), the hospital platform it runs in at CGMH (category 1 and 4, owned by the hospital) and the site configuration (mapping, rules, settings). It does not cover the hospital's EMR, REDCap or sponsor EDCs, which stay the hospital's or the sponsor's systems.

## 3. Deliverables and order

1. User requirements (TB-PLAN-05 §5), functional specifications per workstream, the design specification (`docs/ARCHITECTURE.md` and the design reviews), the risk file (§6), the test specifications (§8), the traceability matrix (`25-traceability.csv`, generated by `tools/gen_traceability.py`).
2. This plan, signed, before any IQ step.
3. Executed IQ (appliance variant at the Japan site; hospital-platform variant at CGMH and on any interim host), executed OQ on a second sample the mapping was not tuned on, the real-data accuracy dry run (100 charts per site) and the blind re-entry test for prefill (TB-PLAN-05 §7.3), executed PQ per the 37 journeys on real studies.
4. The release record of the go-live release: release notes, change classes, the matrix with pass or fail per requirement, the test summary, the model qualification records per tier, the SBOM and notices, the supplier assessments (including the hospital platform), the signed IQ, OQ, PQ and the deviations, reviewer hours spent per pull request.
5. The validation summary report per site, signed per §2.
6. The vendor assessment pack the hospital files: Aimedics' QMS-lite description, the SDLC evidence (CI, review records), the test summary, the SBOM, the release records, the incident and change procedures.

## 4. Frozen release and change control

OQ and PQ run on a frozen release identified by `release.json`; no code item lands after feature complete (TB-PLAN-05 §4.1 G3); only site configuration (CC6) and documents change after it, each with a change record and, for a mapping change, a re-run of the OQ mapping sample. After go-live, changes follow TB-PLAN-05 §7.5 (classes CC1 to CC6, the staged rollout, model change control through the qualification command).

## 5. Data for qualification

Synthetic and public data in every environment that is not the hospital's; pseudonymised site samples only on the site's hardware, after the DPA, where the IRB allows, per the data-handling rule (`sites/data-handling-rule.md`). The OQ sample is different from the mapping sample. The dry-run charts belong to the PI's own study under the PQ protocol.

## 6. Acceptance criteria that may not be waived

IRB approval covering the use; the signed DPA; PQ at 0 fail on the H functions; the pentest letter with no open High on the final digest set; the shared-host isolation tests passed; the backup restore drill passed; the real-data dry run within its thresholds (wrong-exclusion rate ≤ 2 %, listed-candidate PPV ≥ 0.6; post-confirmation prefill accuracy ≥ 0.98); every reveal audited. Every other item may carry an owner-signed deviation with a date.

## 7. Periodic review

Six-monthly after go-live, and after any incident: the risk file, the drift chart, the qualification records, the deviations, the override report, the delegation-log comparison, the training records and the open change requests, reviewed by the owner, the safety-core engineer and each site's PI and steward (CGMH with the second reviewer); the outcome recorded in the release record.
