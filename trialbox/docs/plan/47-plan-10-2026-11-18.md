### 1.0 Calibration: how much assurance this product needs

You asked whether this is overdone for ordinary software ("Not sure what do you need … tend to overdo?") [owner].
In parts it is, and the criticism is taken: this is the honest calibration, and the plan can be run lean [opinion].

**What the product is.** A list-making aid: it proposes candidates and a person (the coordinator, the investigator)
decides every case. It is not a medical device (its claims are kept that way: 10C-5, criterion 17), and it is not the
system of record (the chart and REDCap are). Its failures cost a coordinator's time or a missed candidate the manual
route can still find; they do not change a treatment. So the real harms at the first site are few, and the work that
prevents them is kept at full strength:

- **The data is read correctly**: the SS-MIX2 reader's four faults and the synthetic Japanese hospital that tests it
  (10B-1 to 10B-11, 10B-16, 10B-21).
- **No patient data leaves, and Japanese identifiers are masked**: the guard (10C-1), counts only out (Track D),
  hardened containers and egress checked (10G-1, 10G-49).
- **The engine never silently excludes**: the two compile defects (10A-1, 10A-2) and "unknown never excludes" (C-2).
- **A small IT team can install and run it**: Track K.
- **The words are right enough for a coordinator to trust**: the Japan profile and wording (Track C, 9k-16).

**Assurance beyond ordinary software**, which can be lowered, deferred or dropped without changing any feature:
certifications (ISO 27001, ASVS scoring, SSDF mappings); the paid penetration test; the accuracy bound proven on 124
eligible patients as a release **gate** (it can be measured and reported instead); formal IQ/OQ/PQ records beyond
what a hospital asks for; outside readers and writers; mutation-score targets; part of the architecture-quality
track; measuring tiers beyond the one actually shipped (the 32 GB site box and the head box); the EDC module.

### 1.1 The product, as you framed it

TrialBox is **a patient-finding engine with services around it**. One engine answers "does this patient meet these
criteria, as far as the record can say?" for coded data and notes alike, with "unknown never excludes" as its first
rule [15, read]. Every use (a sponsor's multicentre trial, a single-centre trial, an investigator-initiated study, a
registry, a post-marketing survey, later reimbursement) is a service that reads the same answers: feasibility counts,
the weekly list, a watch-list with the date a patient will qualify, one patient against every open study, alerts on a
new result, co-enrolment checks, exports [15, opinion]. The engine and its services are **shaped per site** (the
hospital's codes, documents and habits are data the steward fills, not code) [12, opinion], **per country** (a Japan
profile: law, committees, roles, words, forms, calendar) [11, opinion] and **per tier** (what each machine can do is
one record the whole product reads) [13, opinion]. It is **multicentre by construction**: a coordinating centre signs
a study package once; each hospital's box imports it, adapts only listed local fields and sends back only signed counts
[14, opinion]. No patient data ever leaves a hospital. It arrives **as a prepared machine** that a small hospital IT
team finishes in a Japanese browser wizard, with no file to edit and no command to type, and one page shows what the
site has and what it does not, and why [18, opinion; decisions 96, 101 ruled].

**At the first site, two boxes** [19, opinion; decision 32 ruled]. The hospital's box has a 32 GB consumer card
(an RTX 5090): it screens the hospital's own patients every night against studies it imports, and never reads a
protocol. Your workstation card is the **head box**: it reads and compiles protocols, runs each package's tests and
holds no patient data. A signed package goes in on media; only signed counts come out. The same package is how every
later hospital receives a study, so the first site exercises the multicentre path from its first study.
