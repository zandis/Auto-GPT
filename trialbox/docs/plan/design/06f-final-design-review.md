## 0. Summary

**Overall: 3.5 / 5** (unweighted mean of the seven scored areas, 24.6 / 7 = 3.51, not rounded up). The design set is the most consistent and most clinically grounded version so far (TB-REV-006e gave the clinical side 4.2). Its weakness is now a different one: **it is still written as a gated hospital pilot plan, and the owner has moved to a five-step development build on synthetic data.** Only two lines in the whole set cite `SIMPLE-PLAN.md` (TB-DS-00 header note, TB-DS-19 status line). Nothing maps the five steps to the 426 functional requirements, 56 non-functional requirements and 37 screens, 351 of which are tagged M1 "pilot release". A builder who opens the set today cannot tell which of them belong to step 1 and which belong to the day a hospital turns on real data.

What is good and should be kept as is:

- The **clinical design** (TB-DS-17, TB-DS-09 S5/S6/S8/S16/S18, BD-04, BD-13, BD-18, BD-19) is right for Japanese and Taiwanese sites: pseudonyms in mail, chart number after an audited reveal, one mark vocabulary with no "ineligible" wording, the treating-doctor rule (主治医の了承 / 主治醫師同意), the `tb_screening_no` link to REDCap that costs the CRC nothing new, the contact-outcome → status mapping, the annual progress-report export for the research office. These are the parts a hospital will notice, and they are simple for the people who use them.
- The **architecture** (TB-DS-02) is honest about what is built, lists its technical debt (TD-1..TD-11) and makes low-maintenance choices (one compose project, HAPI stays, MinIO out, filesystem object store, SQLite queue, no Kubernetes, no blockchain).
- The **completeness audit** (TB-DS-19, 19a) is exactly the right kind of document: 74 rows, each with deck / document / code status and the fix. It found the real gap (ordinary product pages) and wrote it down once.
- The **ecosystem survey** (TB-DS-05) is current to the day, licence-aware, and its build-versus-reuse picks are right (§6 below lists the few additions).

What should change, in one sentence each (details in §3 and §4):

1. Write a one-page **build map** that assigns each of the five SIMPLE-PLAN steps its requirement IDs and screens, and re-tag everything else **H** (only when a hospital uses real patient data) or **L** (later). The M1/M2/C scheme and the pilot-dates paragraph belong to the hospital stage, not to the build.
2. Specify the **synthetic hospital** the plan promises (500,000 patients, Japanese- and Taiwanese-style records, notes in each language): today the code generates 600 generic patients per site (`tools/make_fixtures.py`) and a 50,000-patient structured run (`eval/hospital_sim`), and the 5,000-patient Japanese fixture in TB-DS-04 §3.4 has no generator. This blocks step 1.
3. Take the **hospital-stage process out of the development build**: TOTP and the TOTP step-up, the `auditor` role, the ethics-approval gate on SCREEN, the two-phase pilot wording, the baseline / SUS / NASA-TLX / chart-review machinery, the pentest and IQ/OQ/PQ. None of it is wrong for a hospital; all of it is friction and scope for a build on synthetic data.
4. Decide **one home per role** (the role work list) and make the chat box a header field; today S1 "entry page with one input box and tiles" (FR-UI-01) and S16/S8/S17 "role home" (FR-UI-14) are both M1 and the deck shows a third variant.
5. Trim the 37 screens to the ones the five steps need (about 14) and keep the rest as the written backlog they already are.

Blocking for the five build steps: F6-01, F6-02 (step 1); F6-03, F6-07 (step 2); F6-15 (step 3); F6-06 (step 4); F6-13 (step 5). Everything else can be fixed while building.

### 8.2 Method soundness

**Benchmarks.** Three sets with different strengths is the right design: SIGIR (physician-labelled criteria, small), TREC CT 2021/22 (large, noisy labels, audited), MedTxt (real Japanese text, not matching). Adding TREC 2023 and the AD slice (validation note §4) and Chia for routing was good work. Weaknesses:

- **SIGIR is too small to rank the top candidates.** 79 eligible pairs: 4 / 79 = 5.1 % with Wilson 95 % 2.0–12.3 %; 3 / 79 = 3.8 % (1.3–10.6 %); 1 / 79 = 1.3 % (0.2–6.8 %); TrialGPT's 8 / 79 = 10.1 % (5.2–18.7 %). Every "careful" model in the survey's single-model table (Qwen3.5-9B 3 / 2, LFM2.5 5 / 3, Gemma 4 4-bit 5 / 5, Qwen3.5-27B 4 / 8) is inside the same interval, and "better than TrialGPT" is not established on SIGIR alone. The survey says this ("one pair is 1.3 points … overfits") and compensates by re-checking finalists on TREC; that is the correct remedy, and TREC is where the pair-versus-single result (30–45 % fewer drops) and the pair-versus-LFM2.5 trade-off are actually proven. But **the survey tables print no intervals** although the validation note computed them for every rate; a reader of the survey alone sees 3 / 2 beating 5 / 5 and draws a conclusion the data does not support.
- **Most of the 15 new models were tested on SIGIR only.** Only LFM2.5 (two pairings), Ministral 14B and the gpt-oss-120b pair appear in the TREC / MedTxt pair table. "None better" is therefore proven for the finalists and assumed for the rest; acceptable, since the rest were worse on the small set in the direction that matters (more losses), but the survey should say "12 were screened out on SIGIR, 3 were re-checked".
- **Filter first assumes perfect filters** (consumer-GPU note: "the optimistic case"). The survey's headline numbers inherit this and do not repeat the caveat. Real coding errors add losses on the filter side that no model choice can fix.
- **Precision mismatch.** The alternatives were judged at provider precision; the incumbent's card number (4 / 3) is for quantised files. Comparing the incumbent's card run against alternatives' API runs is unfair in the incumbent's disfavour; comparing API against API (1 / 2) flatters it. The survey mixes both in one row. The right comparison for any serious challenger is the exact quantised file on the card against the incumbent's exact file, which the survey's next step 2 proposes for the medical fine-tunes but not for LFM2.5.
- **Audit by the reviewer, not a clinician.** The 6.4 % / 3.6 % chain rests on 30 pairs read by Claude. The AUDIT file says so; the survey ("a hand audit"), the deck and TB-DS-04 G2 do not. The design's own rule (TB-DS-04 §8, pilot recall) is that misses are adjudicated by reviewers; the public-data audit should be labelled with the same honesty.
- **Projection presented as measurement.** TB-DS-04 G2 and NFR-PERF-09 Notes print "≈ 3.6 % (2.1–5.6)" as the measured value of a gate whose threshold is 5 %. It is a model (raw rate × Beta(11, 21) audit share × 42 % routing). The CI crosses the gate. Either the gate reads "point estimate ≤ 5 %" explicitly or the sample is widened (the survey's own suggestion of 100 site-adjudicated pairs, consumer-GPU note).

**Japanese.** Covered as well as public data allows: SIGIR JA is machine-translated (stated), MedTxt is real Japanese and gives the one honest Japanese number (69 % recall, no excess wrong blocks). **Question (a) of the placeholder (pair, or one model with self-check)** was answered only by implication: single models lose 30–45 % more on TREC than any pair, and Qwen3.5-9B alone abstains too much to be a judge (catches 36 % without filters). It is cheap and would tell whether the second model's value is diversity or merely a second opinion; worth one run, not a blocker.

### 8.3 Is the pick right?

**Yes, as the default, with the caveats above.** The reasoning that holds up:

1. Two models that must agree lose fewer eligible patients than any single model on every cohort (TREC 2021/22, 2023, AD slice, SIGIR), by margins that are significant at TREC size. That is the design's safety argument and it survives.
2. Within pairs, Gemma 4 4-bit + Qwen3.5-9B is the most careful on TREC (19.3 % raw) among those that still catch about half the true exclusions (54 %). The one pair that loses fewer (LFM2.5 + Gemma 4, 9.8 %) catches half as many exclusions (26 %), doubling coordinator review, is weaker on real Japanese (61 % vs 69 % MedTxt), and its licence excludes organisations above US$10 M revenue, which is most hospitals. The survey's rejection of it as the default is right; it is worth keeping as a documented option for a site that would rather review more than miss anyone.
3. Bigger is not safer here: the three ~120B models lost 3–6 times more eligible pairs than the 9B verifier on SIGIR and the gpt-oss-120b pair lost more on TREC (24.9 %). This matters for the owner's instinct that a larger or newer model must be better: on this task it is not, and the data says so consistently.
4. Both models are small enough for the hardware tiers the design names; the verifier fits any card; the judge alone fits a 4090 and is the right single model for the `never` policy.

What the pick does **not** yet have: a zh-TW number; a card-run comparison against any challenger; a recorded build; a Japanese fine-tune run. If the step-5 GPU session (survey next steps 1 and 2, about US$6 and two hours) changes nothing, the pick is final. If Medical-Qwen3-Swallow-30B-A3B closes the 15-point Japanese recall gap on MedTxt without losing more eligible pairs, the verifier slot should be re-decided; the design already allows this (CON-12 is a design choice; FR-MOD-06 is the model gate).

### 8.5 The 32 GB gap: what to do

The gap is real and should not be argued away, but it is smaller and better understood than "35 of 32" suggests, and the design already contains the fix it has not measured.

1. **Measure the mode the design uses.** BD-11 / ADR-03 never need both models resident: the judge runs alone by day and in the first night pass; the verifier is swapped in for the pairs the judge blocked. vLLM's sleep mode (TB-DS-05 §11, in use) or a plain stop-start between passes gives this tonight without the swap controller (TD-5), which is only needed for day-time interactive requests. Each model alone fits a 5090 with room. This is step 5's first measurement, before any context cut.
2. **Record the configuration of the 6 Nov run** and re-run it with the verifier at 4-bit and `gpu-memory-utilization` set per container. If the verifier ran unquantised (the API runs did), the 35 GB figure is explained (≈ 17 + 18 GB) and both-resident fits with the 4-bit verifier (≈ 23 GB + KV cache). This is L8-02 and costs one GPU hour.
3. **Only then** try the survey's step 1 (QAT 4-bit Gemma, 4k context). A 4k context is a real cost for Japanese radiology and discharge text (the consumer-GPU note planned 8–16k) and should not be the first lever.
4. **Keep 2 × 5090 as the fallback the design already names** (BD-10 CGMH, R-5). A Japan site that cannot fit one card buys the second; the cost difference (≈ US$5k) is below one month of the coordinator hours the review queue costs.
5. **Gate the result**: the step-5 "Done when" (TB-DS-20) should read "the pair's fit is measured in the time-shared mode and, if attempted, the both-resident mode; the configuration is recorded in ADR-03 and NFR-PERF-08; N-11 passes in EN, JA and zh-TW on the deployed files". FR-MOD-10 already says most of this; add zh-TW and the configuration.
