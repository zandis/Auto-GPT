## 1. Verdict

**Short answer to the owner's question ("are these industrial-standard specifications and design documents, comprehensive and detailed?"): not yet. They are an unusually complete and well-structured *draft* set, clearly above what most start-ups bring to a hospital, but they are not at the standard where a hospital IT security office, an ethics committee or a pharma vendor auditor could baseline, sign and rely on them.**

What is good, and genuinely so:

- The set has the right *shape*. SRS by 29148 clause 9.5 with stable IDs, priorities, verification method and build status; arc42 with all twelve sections, C4 diagrams, interface specifications and ADRs; a security document with STRIDE per container and per flow, an LLM threat catalogue, a controls catalogue mapped to regulations, a DPIA and a prioritised "what is necessary" list; a V&V plan with risk classes, a full requirements-to-test matrix (253/253), a statistically honest pilot protocol (stratified sampling, Horvitz–Thompson weighting, Wilson intervals, blinded dual review) and an open-source survey with licences checked.
- The clinical design is sound in its principles: filter-first, two-model agreement before any note-based exclusion, "Send to PI" never "Exclude", verbatim quote checks, human confirmation on every EDC value, recall-first AE suggestions, 保険病名 / 疑い handling, opt-out registry at S0, patient contact only by the treating doctor.
- The security document is the strongest of the five and is close to what a Japanese hospital security review (安全管理GL, 3省2ガイドライン disclosure sheet) will ask for.
- The V&V document is honest about the schedule: it says plainly that one engineer cannot build the full system by January 2027 and proposes a subset.

Why it is not yet industrial standard:

1. **The documents do not agree with each other.** I found 40 cross-document conflicts (section 3), including the data classification scheme itself (Arch D0–D4 vs SEC C1–C4 + Z0–Z6), the small-cell threshold (5 vs 10), audit retention (5 vs 10 years), session limits (three different absolute timeouts), the date-shift range (±182 d vs ±30 d), the PHI-leak metric (four definitions), the EDC demotion threshold (20 %/30 vs 70 %/50), the recovery-time objective (1 vs 2 days), whether mail may carry identified data, whether investigators may reveal chart numbers, and even the documents' own identifiers (four numbering schemes). A reviewer cannot tell which number is the requirement.
2. **The SRS priorities contradict the delivery plan.** The SRS defines M as "Must for the January 2027 pilot" and marks EDC pre-fill, REDCap write-back and most new features M; the V&V plan then defers EDC pre-fill, the REDCap module, trial conduct, the consortium, EDC-lite and Medplum to February–Q2 2027. Either the SRS priorities or the pilot scope is wrong, and the release rule in SRS §4 ("a release ships only if every Must requirement … passes") cannot be applied.
3. **Several "built" claims are not supported by master `a1e55fa`.** The console has five roles (`admin, coordinator, investigator, viewer, cro`); there is no `pi` or `smo` role. PR #22 (the "PI workbench") is not on master; D-105 is a lake-rebuild decision, not a workbench. D-99 is cited throughout but does not exist in `DECISIONS.md`. The lockout the SRS marks "N" is built. Status columns drive the release rule, so these must be right.
4. **Traceability is broken at both ends.** The architecture cites NFR families that the SRS does not contain (NFR-SEC, NFR-PRIV, NFR-ACC, NFR-USE, NFR-SCAL, NFR-AVL, NFR-MNT). The existing 239 `@pytest.mark.req` markers in the repository use the spec-v4 ID space (S1-xx, SAFE-xx, FR-M5, FR-UX …), which the new SRS neither maps nor mentions, so the "generated matrix" in VVO §6.4 cannot be produced. Many security controls (re-authentication, reveal reason and time limit, break-glass, extract manifests, landing-zone purge, output classifier, injection suite, 12-character passwords) exist only in the security document and have no SRS requirement to be verified against.
5. **Some requirements are not requirements.** Compound rows (FR-FEAS-04 bundles nine deliverables; FR-AUD-01 lists eleven event types), untestable phrasing ("preserving clinical meaning", "no training", "one engineer shall be able to"), design decisions written as requirements (FR-DEID-04 prescribes three named detector types; FR-MOD-01 names model builds), and conditional priorities ("M (if TC enabled)", "M / S") are all things a 29148 review would send back.
6. **Two clinical/ethical gaps need a decision, not an edit.** (a) An LLM-generated consent explainer can be released to patients by the requester (CRC) with no requirement that the released version is the one the ethics committee approved. (b) AE suggestions are routed to the CRC to "decide whether it is an AE"; under ICH E6(R3) and J-GCP the AE/causality assessment is the investigator's.
7. **The schedule to January 2027 is not credible as written**, and the critical path is missing its longest item: ethics-committee approval (including the opt-out notice) at two hospitals, which in Japan typically needs a monthly committee cycle and a submission that is not yet drafted. A pentest is booked against RC1 in the same week features are still landing.
8. **An industrial set has documents this one lacks** (section 4): a data dictionary for TrialBox's own stores, interface control documents with full payload schemas, a UI/UX specification, a risk management file, a configuration management plan, user manuals and SOPs, a terminology/code-mapping specification, and document control (approvals, baselines, change requests).

None of this is unusual for a v0.1–v0.9 set produced in one day; the point is that it should not be presented as "industrial standard" until the consistency pass and the scope rebaseline below are done. My estimate: two focused weeks of document work (not coding) bring the set to a baseline that a hospital IT review and an ethics office can accept.
