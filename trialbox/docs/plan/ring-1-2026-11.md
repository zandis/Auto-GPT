## 3. Ring 1: does, does not, proved by

### 3.1 Does

At each of the two sites, on the site's own machine, with a TrialBox person supervising:

1. **Install, then information.** The box installs at the site with four questions (language, time zone, the first
   administrator, the key passphrase without a TPM), and asks at most 12 more during the install (U-5). A PRODUCTION
   box refuses by name, until each item is filled in: opening a study for real patients, an SAE notice and the first
   real night.
2. **Reads the site's real data where it lies.** CGMH: the CGRD-type SQL views, read-only, through the `cgrd_sql`
   door that exists [read: `services/adapter/sources/cgrd_sql/source.py`]. The Japanese site: its SS-MIX2 storage,
   standard and extended, read-only, through the reader rewritten in ring 0 (10B-1 to 10B-4) and extended here.
   Each night reads the day's change (delta), not the whole hospital.
3. **Every code system loaded at install from one manifest** (V-18 with DB-C1), each with its name, version and hash.
   Licensed systems (ATC, SNOMED CT, UMLS) come from the hospital's own licensed copy, never from this repository or
   the bundle. A missing system warns; it does not stop the install. The site's own codes are mapped in the site
   profile (10B-6, D-1233), each row `verified` or `verify`.
4. **Screens a hospital-sized night** of real patients for the site's first 1 to 3 real studies, under ring 0's rule
   (D-1069): coded criteria by rule; note criteria by the two models; unknown, a single model, or a negated, family
   or suspected quote never excludes; an inclusion "not met" from notes goes to review. The notes are read in
   Traditional Chinese and in Japanese as written, inside the box (D-1093).
5. **In shadow.** For the first 8 to 12 weeks the weekly list is kept from the coordinator until the coordinator's own
   manual pre-screen for the same week is recorded (10A-19). The investigator's recorded decision and the audit chain
   are ring 0's.
6. **Nothing identifying leaves the box.** Masking is on wherever data leaves the box (the support bundle, exports,
   reports, vendor-visible logs and metrics), and the measures that come back to TrialBox are counts only (section 4).
7. **Supervised.** A TrialBox person is present or in a supervised session that the hospital starts, with patient
   pages closed to every role during it (10K-15, RUNBOOK §21). An update is applied by hand, from a stick, with
   rollback (H-95, H-99, 10K-7). The nightly backup runs to the hospital's share, and a restore is rehearsed at the
   site.
8. **Screens and words in the site's language.** zh-TW at CGMH, read by the owner. ja at the Japanese site, read by
   the site's coordinator or the support partner (9k-16). The legal and IT papers each hospital needs before a real
   night are in its language (section 5.1).

- No patient data, no row-level data and no quote ever leaves a site, including to the owner or to TrialBox.

## 4. The owner's data and a real site: measuring without moving data

### 4.1 The rule

The owner's ruling of 2026-11-23 [#639 7099836527]: the owner's own data may be used only on the owner's own machines,
never in this repository, on GitHub, in a cloud session, in a test fixture or in a log that leaves the machine. Only
counts come back. A real site is held to the same rule. Ring 1 measures a real-site run with these five parts:

1. **The box measures itself, at the site.** Every measure in 3.3 is computed on the site's box, by a command that is
   in the release (10G-36's kit, the night and health counts, the shadow table below). No measure needs a row to leave.
2. **One counts file per measure, of a fixed form.** A JSON file whose schema lists every field. Each field is a count,
   a rate, a duration, a version or a hash of a release. It has no identifier, no chart number, no name, no quote, no
   free text, and no date finer than the month. A count from 1 to 9 is written "under 10" [opinion: the threshold
   is a proposal; question 6]. The schema is checked by the command that writes the file, and a test plants an
   identifier, a quote and a day-level date and sees each refused.
3. **A person at the hospital reads it before it leaves.** The file is shown on the console in the site's language.
   The hospital's named person, not the box, sends it to TrialBox. The box has no route to send it (D-1093's egress
   points carry masking, and this file carries none of what masking covers).
4. **The box's egress is recorded.** 10G-49's one-night capture on the site's box counts connections by destination
   class. P9 passes only when no connection goes anywhere the site's network form does not list.
5. **The owner's machines work the same way.** When the owner runs a box on the owner's own data on the owner's own machine, the
   same commands write the same counts files. Only those files leave that machine.

### 4.2 The shadow table (P6 and P7)

Per study, per week, at each site, counts only:

| Count | Meaning |
| --- | --- |
| Coordinator's list | patients the coordinator's manual pre-screen found |
| Box's list | patients the box listed (likely, to review) |
| Both | on both lists |
| Box only, confirmed | on the box's list only, and the coordinator then judged them worth approaching |
| Box only, not confirmed | on the box's list only, and the coordinator did not |
| Coordinator only | on the coordinator's list only, by the box's reason category (excluded by a coded rule, by a note answer sent to review, never seen by the box, data missing) |
| Charts read, minutes | charts the coordinator read for each list, and minutes a chart (10G-25) |
| Box-excluded read | box-excluded charts the coordinator read that month (about 40), and how many of them were eligible |
| Decided share | the share of note criteria the two models decided, by language |

"Coordinator only, excluded by a coded rule" is the line that most needs a person's eye: each one is a finding for
the integrator, written without the patient (the criterion, the rule, the code system and its version).

### 6.2 Where ring 0 is ahead, and where behind

**Ahead** [opinion, from the table and D-1070's ring 0]:
- **Nothing leaves the box.** Both models run on the hospital's machine. Only TriNetX states the same for its data,
  and it returns counts, not a reviewed per-patient list.
- **The harm rule is written and tested.** Unknown, a single model, or a negated, family or suspected quote never
  excludes; an inclusion "not met" from notes goes to review (D-1069). None of the four pages states a rule for what a
  model's answer may not do.
- **Two models must agree** before a note criterion is decided (D-89); TrialGPT uses one.
- **Japanese storage, codes and screens.** SS-MIX2, WHO ICD-10 and Japanese screens are in ring 0; Traditional Chinese
  screens and a CGRD-style SQL door are built. None of the four states Japanese or Chinese notes.
- **The record a site keeps.** The investigator's recorded decision, an audit chain that detects truncation, and a
  rehearsed restore.

**Behind:**
- **No real patient has been screened.** Lind and Deep 6 report real health systems; TriNetX hundreds of millions of
  records. Ring 0 is synthetic by definition.
- **No published figure.** TrialGPT's 87.3 % is peer-reviewed, on public data. Ring 0 states no bound, only a
  measured sheet (rc1 line 8).
- **No embedding in the chart.** Lind and Deep 6 work inside the hospital's record system; TrialBox is a separate
  console fed overnight.
- **No network.** TriNetX's value is its federation; TrialBox's multicentre track is ring 3.
- **No outside assurance.** Lind claims SOC 2; TrialBox's outside test is ring 2.

## 7. Medplum or HAPI FHIR in ring 1

**Recommendation: no. Ring 1 keeps HAPI FHIR, as BD-01 says** (`docs/plan/design/00-baseline-decisions.md:64`:
"Pilot: HAPI FHIR 8.12 stays … Medplum is evaluated after the pilot"). Ring 1 is the pilot. The evaluation stays
after it, in ring 4 [opinion].

**What Medplum would replace.** The FHIR store: today the `hapi` service (`hapiproject/hapi:v8.12.0-2`, pinned by
digest) on the box's one PostgreSQL server, in its own database `hapi` with its own role [read:
`deploy/docker-compose.yml` l. 80, 177 to 182]. That covers the store V-18 loads code systems into, D-1181's value
sets, the backup's `TB_HAPI_DB_URL`, RUNBOOK §17's platform secret, and H-99's `hapi` size read. Medplum would not
replace the console's accounts (BD-01: console-native accounts with TOTP); that is the one thing Medplum is best at.

**What Medplum costs in runtimes.** Medplum's server is TypeScript on Node.js (its from-scratch install uses Node.js
24 and PostgreSQL 16) and needs Redis or a compatible server such as Valkey for jobs and cache [source:
https://github.com/medplum/medplum] [source: https://www.medplum.com/docs/self-hosting/install-from-scratch]. The box
would gain a Node.js server and a Redis-class server, each an image to pin, scan, harden (10G-1), back up and
restore. It would not lose its Java runtime, which the box needs for other parts (`make jvm-deps`). On CGMH's platform
form each is one more workload and one more secret for the hospital's platform team.

**Its risk.** (a) A change of the FHIR store at two real sites while ring 1 is being proved: every backup, restore,
update and terminology path that names `hapi` changes in the ring whose proof is a restore at the site. (b) No public
evidence of JP Core or TW Core support; its public focus is US Core [source: https://www.medplum.com/docs/compliance/onc];
TrialBox validates against JP Core 1.2.0 and TW Core (BD-12). (c) Its FHIR API is R4 with Medplum's own resource types
for users and access [source: https://medplum.com/docs/api/fhir]. (d) Licence is no risk: Apache 2.0, like HAPI.

**What HAPI lacks.** The starter server "comes with no security implementation": no user management, no OAuth
server, no SMART authorisation server, only interceptors to build them [source:
https://hapifhir.io/hapi-fhir/docs/security/introduction.html]. Medplum has OAuth, OpenID and SMART on FHIR built in
[source: https://github.com/medplum/medplum]. That gap does not bite ring 1: TrialBox's FHIR store is internal, reached
only by TrialBox's services with their own role, and no outside app connects to it. HAPI has what ring 1 uses:
terminology, value-set expansion, subscriptions and bulk export [source:
https://hapifhir.io/hapi-fhir/docs/server_jpa/introduction.html].

**When to look again.** When a site asks for outside SMART apps, or for its single sign-on to reach the FHIR store
directly (then BD-01's Keycloak fallback is the smaller step), or when ring 4 widens the data doors.

### 8.2 Main risks

- **Real data reaching the VM.** The only control is people and the rule. A VM box refuses PRODUCTION, and its install
  names it a cloud box on every page [opinion: a card, if the owner wants the VM form kept].
- **Cost running on.** An always-on VM costs about 3,300 US$ a month on demand (below). Every launch carries an
  estimate and a hard cap (D-141) and needs the owner's yes; this page launched nothing.
- **Spot pre-emption.** One pre-emption in about 11.5 spot hours was observed (`docs/plan/32-gcp-test-plan.md`);
  a demonstration in front of people should run on demand.
- **It proves less than it looks.** A VM shows the software, not a site: no hospital network, no hospital storage, no
  site profile. It cannot stand in for any line of 3.3.
- **Regions.** GPU availability and prices differ by region; a Tokyo or Taiwan region is not guaranteed a card.
