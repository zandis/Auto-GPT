# D-321 Scenario rulesets: SQL checked on planted gold, CQL recorded by a local engine

- **Task:** T-504 (TB-PLAN-06 §6.2.6; CGMH scenarios T1, T2, T3)
- **PR:** this branch (`agent/T-504-cgmh-scenarios`)
- **Date:** 2026-11-10
- **Status:** proposed
- **Number:** given by the integrator for this card

## Context

T-504 adds RA-JAK, a synthetic interventional trial on a new Taiwanese rheumatology site (`tools.synth_hospital
--profile tw-ra`). A committed ruleset carries `tests/expected.json`: CQL verdicts recorded from HAPI at build time,
which CI replays against the SQL. This build machine cannot run a HAPI image (registry pull limits and disk). T-503
built its scenario rulesets with SQL checked against the generator's planted gold.

Running the CQL anyway showed a defect. In CQL engine 5.4.0 (the engine of HAPI FHIR 8.12),
`ReplaceMatches('abc', 'x', 'y')` returns `'abc'` with literal quotes when nothing matches. The generated
`TB_Common."UnitOf"` calls `ReplaceMatches` three times, so it never recognises a unit, every `Conv_*` is null and
every derived score (DAS28, eGFR, BMI) is null under CQL. The SQL is right. On a real HAPI 8.12 gate, an approval
of any ruleset with a derived score would fail the equivalence check.

## Decision

1. **A local CQL engine for the build.** `tools/cql_local/` holds the clinical-reasoning engine that HAPI 8.12 runs
   behind `Library/$evaluate` (cqf-fhir-cql 4.13.0, CQL engine and translator 5.4.0), run in process over an
   in-memory repository. `python -m tools.cql_eval --fetch` gets its jars once (Maven, into `.cache/`). It is
   build-time only, like `tools/build_rulesets.py`. `python -m tools.cql_eval --check RA-BIO GZQO RA-COH` replays
   the committed HAPI recordings: it answers as HAPI did on every verdict (3600, 3600 and 1200).
2. **Scenario rulesets are built by `tools.build_scenario_ruleset`.** It compiles the protocol document with the
   stub model's cassette. The approval gate compares the SQL with the planted gold of the scenario's archetype
   (as T-503 did) and must be 100%. Then it records the local engine's CQL verdicts for the test patients in
   `tests/expected.json`, with the SQL-to-CQL agreement per criterion. The build fails on any difference, except
   CQL null on a criterion listed as a known engine defect.
3. **Known differences are named, not hidden.** For RA-JAK they are INC-04 (DAS28) and EXC-11 (eGFR). There the
   recorded CQL verdict is null, `agreement.known_differences` says why, and the CI test checks the SQL against the
   gold instead. The other 12 compiled criteria agree 100%.
4. **No patients file for a regenerated site.** The test patients' FHIR resources would be 14 MB. The site is
   regenerated byte for byte by `tools.synth_hospital`, so `tests/patients.ndjson` is not committed for RA-JAK.

## Consequences

- The `"UnitOf"` defect is for the owner of the CQL generator (a protected file). A fix that avoids
  `ReplaceMatches`, for example `Combine(Split(s, ' '), '')`, would make CQL and SQL agree. RA-JAK should then be
  rebuilt and its `known_differences` removed. AD-MAB EXC-04 (eGFR) has the same problem.
- **Fixed (2026-11-10, with the merge of D-275 and T-613a).** The recompiled shipped rulesets now call `"UnitOf"`
  for every lab and score input, so RA-COH also lost its DAS28 answers under the engine (1014 of 1200). The template
  now uses `"Swap"(s, a, b)` = `Combine(Split(s, a), b)` (with `''` kept as `''`) in `"UnitOf"` and `"UnitKey"`.
  RA-BIO, GZQO and RA-COH replay their HAPI recordings exactly again; RA-JAK was rebuilt and agrees 100% on all
  14 compiled criteria, with no known differences.
- The local engine is not a replacement for the HAPI gate at a site. It is a build check.
