**D-275 Structured criteria: unusable data is unknown, never an exclusion (safety review S-1, S-4, S-5, S-9; MR-002 / R-31).**
Source: the patient-safety review of 2026-11-10 (four findings, each run or read by the reviewer) and assessment row MR-002.

* **Units (S-1, MR-002).** The compiled SQL compared a lab row's number with the criterion's number whatever the row's unit was: a creatinine of 90 umol/L failed "<= 1.5 mg/dL", and an HbA1c of 53 mmol/mol met the exclusion "> 10 %". Now a row is compared in the criterion's unit (`Atom.value.unit`): used as it is when the units are the same, converted when the row is an analyte of `tb_common.derived.UNITS` (creatinine, CRP, ESR, weight, height) and both units are in its table, and otherwise it has no usable number. A row with no unit is the same: unknown. Such a row never makes a comparison true or false; the answer is unknown unless the readable rows settle it, with the new reason `unit_mismatch` (en / ja / zh-TW). A criterion with no unit (a count, a score) reads rows with no unit only. `libs/tb_common/labunit.py` holds the rule and its SQL twin; `libs/tb_common/derived.py` is unchanged.
* **Record status (S-4).** A record whose own status says it is not a fact reaches no lake table: an Observation `entered-in-error` or `cancelled`; a MedicationRequest `entered-in-error`, `cancelled`, `draft` or `not-taken`; a Procedure `entered-in-error` or `not-done`; a DiagnosticReport `entered-in-error` or `cancelled`; a DocumentReference `entered-in-error`. It can neither meet a criterion nor exclude. A stopped or completed order and a preliminary result still count. The OMOP store keeps the record with status `rejected` and exports it to no table. SS-MIX2 ORC-5 `CA` is now `cancelled` (it was `stopped`, which counts).
* **Sex (S-5).** `patient.sex` holds `male`, `female` or nothing; `other` and `unknown` are no value (both lake sources). The SQL and CQL also check it themselves, so a lake built earlier is read the same way. A sex criterion is unknown for such a patient, eGFR has no value (reason `derived_missing_input`), and "female and positive pregnancy test" is unknown, not false.
* **Order dates (S-9).** A medication-duration atom is unknown when the dated periods do not reach `min_days` and a matching order has no end date (and began on or before the window's end) or no date at all; the new reason is `order_dates_missing`. It was "1 day" and FALSE. The adapter no longer drops an order with no date: it is kept, reported, placed in no window, and leaves "any order in the window" unknown.
* **Approved rulesets.** A ruleset's SQL is stored at approval and run as stored, and the five shipped rulesets were approved before these rules. Recompiling needs a new approval, so `criteria_compiler/compile_sql/overlay.py` runs the stored SQL beside a fresh rendering of the same approved criteria and ValueSets and keeps a stored answer only where both agree; where they differ the answer is unknown. The fresh rendering never decides anything on its own, and the stored text is embedded unchanged. SQL compiled from now on carries a `-- Safety rules: D-275` line and runs alone. The cascade, the SQL engine (NAV, MICROBATCH, CASE), FEAS, COHORT and `tools/nav_retro.py` all use it. One effect to know: the guard also brings the earlier unknown rules (D-113, D-142, D-149) to the shipped rulesets, where those decisions had left them for the next compile.
* **Impossible score inputs (after D-189/190).** The Python reference gives no value and `derived_unit:<component>` for an input outside `derived.DOMAIN` (a joint count over 28, a negative CRP or ESR, a creatinine of 0 or less, a number that is not finite). The SQL and CQL engines used the number: a TJC28 of 40 gave a DAS28 that met "> 5.1", a creatinine of 0 an infinite eGFR. Each converted input now goes through the same domain check in both generators (`domain_sql`, `domain_expr`), so the score has no value with the same reason. DAS28, CDAI, SDAI, ASDAS and eGFR are covered.
* **Second review (F1 to F13).** *A status nobody can read is never a fact.* The mapping engine has `unmapped:` beside `default:`: a code the map does not know no longer takes the empty default. The shared TW mapping (the JP SS-MIX2 site and the CSV and CGRD templates extend it) maps an order's `cancelled`, `entered-in-error`, `draft` and `on-hold`, and a lab result's new optional `result_status` column; any other code is FHIR `unknown`. An empty status is `unknown` tagged `urn:trialbox:status-source|not-recorded`, and the record counts as before (a HIS that keeps no status). Before this a cancelled SS-MIX2 order (ORC-5 `CA`) still became `active` through the site mapping and met a "prior drug" exclusion. The SS-MIX2 reader passes an ORC-5 it does not know as it is (it fell back to `active`), maps `ER` to entered-in-error, and reads OBX-11: `D`/`W` entered-in-error, `X`/`N` cancelled, `P`/`R`/`S` preliminary, `I`/`O` registered, `F`/`U` final, `C` corrected. In the lake an order of `unknown` status is kept with no date (unknown, as an undated order), and a `preliminary` or `unknown` result keeps no value (unknown, as a text result), unless tagged not recorded. Also not facts now: a `registered` result, a `preparation` procedure, a `cancelled` or `entered-in-error` encounter. *Bounds.* A converted value is rounded to 6 decimals in Python, SQL and CQL, and the factor is the shorter exact decimal (`/ 88.4`, `* 0.45359237`). 1.5 mg/dL against "<= 132.6 umol/L" and 309.4 umol/L against ">= 3.5 mg/dL" were FALSE (132.60000000000002, 3.4999999999999996); the CQL factor 0.01131222 put 132.6 umol/L above 1.5 mg/dL. *Guard.* The guard renders per criterion when the whole set does not render: a criterion the generator refuses is unknown for itself only (it failed the whole job). A disagreement says `rules_changed` (a more specific reason such as `unit_mismatch` is reported first), not always `unit_mismatch`. The mark counts only in the SQL header, so a criterion text holding it cannot switch the guard off. The guard is built once per ruleset content. An empty `Quantity.code` is no code in CQL, as in the lake. *FEAS, RA-COH.* `synthetic-tw-a` loses one patient from "remaining" with "unknown" unchanged. The approved RA-COH SQL predates D-149 and built a DAS28 from two visits (the joint counts of one day with the patient global of two months before), which met "> 5.1". The guard applies the same-visit rule: that date has no value. The patient's other visit gives a real DAS28 of about 2.7, and FEAS counts "a known FALSE at some date, never TRUE" as not remaining (D-18). The old TRUE was not a measurement, so this is correct; FEAS's attribution of a lost TRUE is listed in Open.
* **CQL.** The CQL generator and `TB_Common` carry the same rules, so the equivalence gate of the next compile compares like with like. They translate with cql-to-elm 5.4.0; they were not run on HAPI here.

*Where.* `libs/tb_common/labunit.py`, `libs/tb_common/reasons.py`, `services/criteria_compiler/compile_sql/{generator,overlay}.py`, `services/criteria_compiler/compile_cql/`, `services/criteria_compiler/semantics.py`, `services/lake/flatten.py`, `services/omop/{load,export}.py`, `services/adapter/pipeline.py`, `services/adapter/sources/ssmix2/source.py`, the five callers of the stored SQL.
*Evidence.* `tests/unit/test_criteria_safety_review.py` (SS-MIX2 storage through the reader, the real JP site mapping, the lake and the SQL; bounds in three engines; the guard's per-criterion fallback, reason and mark); `tests/unit/test_criteria_safety.py` (lake -> SQL -> both engines, the shipped GZQO as approved, the OMOP lake against the legacy lake, the CQL through the translator, impossible score inputs against the Python reference); each case was a hard exclusion or a silent false before. `tests/integration/test_ingest_inproc.py::test_undated_medication_orders_are_kept_and_reported` replaces the test that held the drop. The ATOMS snapshots changed.
*Not done.* No unit table beyond the five analytes: g/dL against g/L, 10*4/uL against 10*9/L, % against mmol/mol are unknown until a tested factor is added. `rulesets/` is untouched: the shipped SQL, CQL and ELM are as approved. An existing lake keeps void records, text sexes and the dropped undated orders until the next ingest (RUNBOOK §5).
*Open.*
1. **v1 semantics (owner).** Every shipped ruleset still reads a FALSE structured inclusion as a hard exclusion. This entry makes sure missing, void or unreadable data gives unknown, not FALSE. It does not cover a patient with no coded record at all for a presence criterion ("no order", "no diagnosis"): that is FALSE by design (D-130 covers unreadable code systems only). Moving the shipped rulesets to "only an affirmative record excludes" is a ruleset change and needs the owner and the PI.
2. **Recompile the shipped rulesets** under the compose stack (CQL, ELM, equivalence, `expected.json`) and re-approve, so they carry the rules themselves; the guard costs a second evaluation of each criterion until then.
3. A numeric criterion extracted with no unit is compiled and then reads every row that has a unit as unknown; the compiler should flag it for the reviewer.
4. Rows quarantined at validation (up to 0.5 % per table) are still invisible to matching (S-9 b, second half). Cancelled appointments are not filtered (they only set the screening scope).
5. FEAS counts a patient whose only TRUE turned unknown, beside a known FALSE at another date, as dropped by the FALSE (D-18 attribution). Counting them as unknown is a FEAS change, for the owner.
6. An old order with no end date makes a duration criterion unknown for good (safe, but noise); an order of `unknown` status and a `preliminary` result are unknown in the CQL only through the lake's rules (CQL is compile-time).
7. Goldens: the goldens owner re-blesses after review (`make goldens REASON="D-275: ..."`); candidate counts do not move.
