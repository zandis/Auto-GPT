# D-879 An account notice leaves the box (NOTICE-ACCOUNT)

- **Task:** a defect found while planning T-715 refuse mode for the notices, lane C2. D-719 tells the data stewards (a disabled one too) and the PI of each of the account's studies when someone else set a factor of an account (the holder is told in the console at the next sign-in); the console sends it as a notice of kind `ACCOUNT`, which the orchestrator's `POST /notices` refused (422: only N1, N2, BG and HEALTH), so no account notice ever left the box and the console's best effort recorded each as not sent. · **Date:** 2026-11-17
- **Decision:** the orchestrator accepts the kind `ACCOUNT`, like every notice an aggregate mail to hospital addresses only (an outside address is refused, 400), audited `notice.sent`; an unknown kind is still refused. The adversarial review added: the console sends each person a mail of their own (a notice takes five recipients at most, and one refused address refused everyone's), counting a failed one in `console.account_notice`; and an account notice's mail key carries the instant, not the day, so a second reset of the same account the same day is a mail of its own, never dropped as a duplicate while recorded as sent.
- **Left:** the notices move to refuse mode (T-715) on its own card. A mailbox outside the hospital's domains is still accepted when an account is made (the notice to it is refused and counted).
- **Held by:** `tests/unit/test_an_account_notice_leaves_the_box.py` (a real orchestrator in PRODUCTION with per-service tokens) and `tests/console/test_an_account_notice_reaches_each_person.py`, synthetic only (failing output on the previous code kept: `notice-fail.txt`).
