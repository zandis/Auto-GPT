**D-276 The two-model check needs two different models, sees all its evidence, and has a test for every rule (deep review LLM-002, LLM-003; safety review S-2, S-3, S-10; assessment P-34).**

* **A failed judge is a failure, not the verifier's answer (LLM-002, Critical).** The `patient` route lists the judge build, then the verifier build. When the judge's server returned an error, the gateway answered the role `judge` from the verifier build. The verifier then confirmed its own answer: "both agree", no failure counted, and a note answer could exclude. The install left `TB_GATEWAY_MODEL` empty, so the judge named no build. Three changes. (a) Roles of the `patient` group never fall back to another alias: a route has `fallback: none | any`; it is `none` for the routes that serve that group (`models/routing.yaml`, refused otherwise), and the gateway applies it to those roles on any route (`RoutingPolicy.no_fallback`). (b) `deploy/install.sh` writes `TB_GATEWAY_MODEL=j-workhorse` on the pair profiles. (c) The note judge compares which build (the gateway's `build_sha`) and which served name answered each of the two: the same twice means the judge did not answer, `unknown` / `model_down`, counted as a failure, so a run where the judge is down fails (`check_judge`) instead of listing patients judged by one model.
* **Two different models (S-2).** A verifier that was the judge again (the same endpoint and name, `LLM_VERIFIER_MODEL` left unset, or the judge's alias named twice) was accepted as "both agree", so one model alone could exclude a patient. Now the pair is checked three times. (1) *As configured*, before each run (`tb_common.pair.same_model`, used by `effective_note_block`): one client, the same gateway asked for the same alias, the same model name on any URL, a model with no name, or two names that one endpoint serves from the same weights (`/models` gives both the same `root`) are one model. The run then never excludes on a note answer and says why. (2) *As answered* (`tb_common.pair.combine`): two answers that come back under one served model name or one gateway build are `unknown` / `model_down`, counted as a failure (see LLM-002). (3) *In the canary*: a pair that is one model fails the self-test, so the gate stays shut. Names are compared case-folded with spaces trimmed, nothing else: `local/x` and `x` stay two names.
* **Fails closed (adversarial review F-02, F-03).** "Cannot tell" counts as one model. On the direct path the weights each endpoint serves (`/models` `root`) are compared on any URLs; an endpoint that gives no `/models`, errors, times out, does not list the name or gives no `root` makes the pair one model. A judge through the gateway and a verifier straight to an endpoint (or the reverse) cannot be compared: one model. A gateway judge that names no alias gets the default build (`trialbox-stub` in DEV/TEST, `j-workhorse` elsewhere) in the comparison. A direct answer now carries the name the server answered under.
* **Every screening path takes the same decision (review F-01).** MICROBATCH worked out the tier again with the configured policy alone, so on a one-model box a note answer could still exclude. `tier` now requires `note_block`, and MICROBATCH passes `effective_note_block` of its judge, as SCREEN, NAV and CASE do.
* **Consent (review F-04).** A verifier that is the judge again does not check consent statements: they are marked unverified, and the refusal is audited (`llm.pair.same_model`).
* **Said out loud.** At start the orchestrator logs `FAIL` and writes `llm.pair.same_model` to the audit (`canary_gate.check_pair`, gate on or off). `trialbox doctor` fails `note_block` in every environment, and in VALIDATION and PRODUCTION also fails a direct verifier (`LLM_VERIFIER_BASE_URL`), whose weights it cannot confirm: use the gateway verifier build. The run's judging record carries the reason.
* **The stub box.** The registry has a second stub build, alias `stub-verifier`, served name `stub-verifier`, routed only when named; `deploy/poc.sh` and `poc.ps1` name it as the verifier. Before, the stub box named `trialbox-stub` twice.
* **All the evidence (S-10).** Both models read the same excerpts (2,500 tokens). When a note holding evidence did not fit, or was cut so that an evidence sentence was lost, an answer that would exclude is no longer final: `unknown`, "not evaluated", a person looks (`engine._Run.excerpt_set`, `_map`). An answer that keeps the patient stands. The same on the v1 path (`evaluate_patients`: NAV, MICROBATCH): when the chunk budget cut retrieved chunks, the full-record read gets its turn; when that is cut too, `unknown`.
* **The stub refuses names it does not serve (S-3, P-34).** `services/llm_stub` answers 404, as vLLM does, to a model name outside `TB_STUB_MODELS` (default: `trialbox-stub`, `stub`, `stub-verifier` and the pair's two served names). `/v1/models` lists them. Test personas, by model name: `stub-dissent`, `stub-lowconf`, `stub-badquote`, `stub-olddate`, `stub-down`. No shipped setting names a persona.
* **One test per rule.** `tests/judge_kit.py` (scripted judge, scripted models, a small note lake). Each rule below was removed in turn and its test failed (the table is in the pull request): the confidence floor, an unverified quote, S4 disagreement, no note in the window, S2b below for an inclusion, the index sweep in a screening run, no embedder, the strict last round and the judge's wake failure of the one-GPU rounds, a structured inclusion with no value (v1), a scoped patient missing from the cascade result, a consent table error.

*Changed tests.* `test_note_pair_disagreement.py`, `test_one_engine.py`, `test_screen_cascade.py` and `test_agreement_judge.py` gave the judge and the verifier one model name or build; each fake is now its own model. `test_canary_gate.py` and `test_judge_tier.py` used verifiers with no name or weights; they now name two models. `test_judge_tier.py` and `test_mixed_and_polarity.py` called `tier` without the run's decision. `tests/integration/test_screen_inproc.py` expected MICROBATCH on the one-model in-process box to exclude on a note answer; it now expects review. `test_gateway.py::test_production_refuses_unpinned_and_non_champion_builds` expected an unpinned judge build to fall to the verifier build; it is now refused (LLM-002). `test_two_model_identity.py` first asserted "no `/models`: names decide"; it now asserts the opposite (fail closed).
*Evidence.* `tests/unit/test_cascade_exclusion_rules.py`, `test_screen_exclusion_pair.py`, `test_two_model_identity.py`, `test_two_phase_strict.py`, `test_llm_stub_served_names.py`, `test_microbatch_note_block.py`, `test_gateway_no_fallback.py`.
*Open.* (1) On the direct path the weights are compared by the `/models` root (a path), not by a hash: two copies of the same weights in two folders look like two models. Use the gateway (its build hash is compared). (2) For S-10 the cascade does not read the left-out notes in further rounds; it asks a person. Paging the rest to both models is the other option. (3) Retrieval caps are not counted as left-out evidence (review F-05): the v1 chunk search returns the five best chunks (`orchestrator/scenarios/evaluate.py`, `chunks_search(k=5)` in `NoteJudge._chunks`); the cascade's S2b keeps the five best sentences, or the first five without an embedder (`matching/cascade/engine.py`, `_Run.s2b`; `s2b_semantic.screen(k=5)`); a long note cut to its evidence sentences (`_clip`) loses the sentences around them, which may say "ruled out". Sending every capped answer to review would stop most note exclusions; it needs an owner's decision. (4) The judging record has no separate count of answers given twice by one build; they count as failures. (5) A box whose pair is one model never excludes on a note and says so in the audit, the log, the doctor and the run page, but raises no console alert (review F-07). (6) `tools/cascade_e2e.py` (offline, not patient-facing) still lets one model exclude when no verifier is set (review F-06). (7) The stub serves its personas whatever `TB_STUB_MODELS` says (review F-08). (8) The S-10 replacement reads "not evaluated" although both models answered (review F-09).
