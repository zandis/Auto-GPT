# D-877 One sign-in per person on a test box, and the role it acts in (STEPS-ROLE)

- **Task:** STEPS-ROLE, on the owner's ruling D-1063 (2026-11-17), lane C2. On the test VM's steps mode (D-1062) each tester had four accounts (admin, coordinator, steward, investigator); the owner wants one sign-in per person and a way to choose the role. · **Date:** 2026-11-17
- **Decision:** an account may hold extra roles (`users.extra_roles`), granted only by the boot tool `python -m console.steps_roles NAME ROLE,ROLE,...` (the first role is the account's own; one-time enrolment code; `--flag-on`), never by a console page. The session carries the acting role, and `UserStore.session` (the one place a request's role is resolved) puts it on the session's user, so every permission check, scope rule and actor assertion reads it as it reads an account's role; the user name stays (delegation log standing, audit trail, erasure records). `POST /role` (CSRF) switches it, audited `role.acting` (user, from, to); the top bar shows the acting role and the select (en, zh-TW, ja). Gates: the audited flag `steps.acting_role` (default off); with `TB_ENV` VALIDATION or PRODUCTION (unset is PRODUCTION) the flag cannot be set, roles cannot be granted, the switch is refused, and the console refuses to start with the flag on or an extra role on record; with the flag off an account is its own role only, and a stored acting role that no longer applies is ended (a new switch is audited). The adversarial review added: an account that may act in a protected role is held as protected (D-719: one factor at a time, a second person where there is one), and `/ops/flags` names the test-box refusal. No role's rights change.
- **Left:** the second-person rules (D-719 confirmations, break-glass reviews) compare user names, so one person switching roles never confirms their own request; a person acting as steward is not counted as a steward who may confirm (the second person stays a real steward account). Steps that are split by role rather than by person (a criteria approval, the EDC switch-on) can be done by one person holding both roles, which is what D-1063 asks for on a test box. The test-box checks read the environment of the process that runs them: the boot tool pointed at a production database with TB_ENV=TEST would write there, and that console then refuses to start (fails closed). The demo VM's boot calls the tool (the integrator wires `TB_DEMO_VM_PEOPLE`).
- **Held by:** `tests/console/test_one_sign_in_acting_role.py` and `tests/console/test_role_route_matrix_acting.py` (the router table walked once per acting role: no route opens beyond the role's own design column; acting as the administrator answers every patient-level route as the administrator does, D-280), synthetic accounts only (failing output on the previous code kept: `steps-fail.txt`).
