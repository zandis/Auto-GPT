# D-877 One sign-in per person on a test box, and the role it acts in (STEPS-ROLE)

- **Task:** STEPS-ROLE, on the owner's ruling D-1063 (2026-11-17), lane C2. On the test VM's steps mode (D-1062) each tester had four accounts (admin, coordinator, steward, investigator); the owner wants one sign-in per person and a way to choose the role. · **Date:** 2026-11-17
- **Decision:** an account may hold extra roles (`users.extra_roles`), granted only by the boot tool `python -m console.steps_roles NAME ROLE,ROLE,...` (the first role is the account's own; one-time enrolment code; `--flag-on`), never by a console page. The session carries the acting role, and `UserStore.session` (the one place a request's role is resolved) puts it on the session's user, so every permission check, scope rule and actor assertion reads it as it reads an account's role; the user name stays (delegation log standing, audit trail, erasure records). `POST /role` (CSRF) switches it, audited `role.acting` (user, from, to); the top bar shows the acting role and the select (en, zh-TW, ja). Gates: the audited flag `steps.acting_role` (default off); with `TB_ENV` VALIDATION or PRODUCTION (unset is PRODUCTION) the flag cannot be set, roles cannot be granted, the switch is refused, and the console refuses to start with the flag on or an extra role on record; with the flag off an account is its own role only. No role's rights change.
- **Left:** nothing in the product; the demo VM's boot calls the tool (the integrator's wiring of `TB_DEMO_VM_PEOPLE`).
- **Held by:** `tests/console/test_one_sign_in_acting_role.py` and `tests/console/test_role_route_matrix_acting.py` (the router table walked once per acting role: no route opens beyond the role's own design column; acting as the administrator answers every patient-level route as the administrator does, D-280), synthetic accounts only (failing output on the previous code kept: `steps-fail.txt`).
