# 4. Troubleshooting

**Reader:** the box owner, with Aimedics on request.

| Symptom | Check | Fix |
| --- | --- | --- |
| No reply to a mail | `docker compose logs mail-gateway --since 1h` | sender not allowed, SPF/DKIM failed, or the rate limit; the log says which (no PHI) |
| "Today's limit is reached" on the console | `settings.yaml`: `rate_limit_per_sender_per_day`, `rate_limits_per_day` | the limit counts each heavy run type (FEAS, SCREEN, COHORT, NAV, MICROBATCH, CALIBRATION) per sender per 24 h; raise it, or set `rate_limits_per_day: {SCREEN: 40}` (0 = no limit) and restart the orchestrator (D-146) |
| "Ruleset X has no approved version" | `git -C /data/rulesets tag` | paste the protocol, then the investigator approves on S20 |
| Ingest `passed: false` | `ingest_report.json` → `errors` | the hospital changed its export: run `mapping_check.py`, fix the site mapping |
| Equivalence gate under 98 % | the review sheet "equivalence" | edit or reject the flagged criteria |
| SUBMIT refused | the reply names the check | NAV older than 14 days: rerun NAV |
| Lake slow or out of memory | `docker stats` | raise `TB_LAKE_MEMORY_LIMIT` (default 40 % of RAM; spills to `/data/lake/tmp`) |
| A job fails with `LAKE-LIMIT` | the job's error; `df -h /data` | the query hit its spill cap (`TB_LAKE_MAX_TEMP`, default a quarter of the free disk, at most 50 GB; `TB_LAKE_TEMP_DIR` moves the spill) and was stopped before it filled the disk. Usually a join that multiplies rows: report it; raise the cap only for data that really is that large |
| A lake rebuild reads `interrupted` | `GET /rebuild/<snapshot>` on the lake; the lake's log; `docker stats` | the build runs as a process of its own (`TB_LAKE_BUILD=process`, D-539) and that process was killed, usually by the kernel at the lake container's memory cap; the lake went on answering queries. Start the rebuild again (the publish does on its next tick); if it is killed again, raise the lake's cap or lower `TB_LAKE_MEMORY_LIMIT`. `failed` with an exit code means the process ended by itself: its error is in the lake's log |
| The night's ingest reads `failed: the ingest's process ended without an answer` | `GET /run/<id>` on the adapter (or `<lake>/adapter-runs/<id>.json`); the adapter's log; `docker stats` | the night runs as a process of its own (`TB_ADAPTER_RUN=process`, D-663) and that process was killed, usually by the kernel at the adapter container's memory cap, or the box restarted; the adapter went on answering. Run the night again (the scheduler does at its next start); if it is killed again, raise the adapter's cap. `failed` with an exit code means the process ended by itself: its error is in the adapter's log |
| A job fails with `LAKE-STALE` | the job's error; `trialbox doctor`; the adapter's last runs | the newest lake snapshot is older than `TB_LAKE_MAX_SNAPSHOT_AGE_DAYS` (3 in the production compose file; 0 turns the check off) before the job's run date, so the nightly ingest has not published for days (D-383). Fix the ingest and let a night publish, then run the job again; raise the limit only when a gap in the feed is known and accepted |
| Two or more files for one date under `<lake>/db/gen/` | `ls <lake>/db/gen/` (`<date>.g<n>.duckdb` and `.json`: the number, the cause, the lake's hash); `ls <lake>/holds/` (each hold names its `generation`) | every build of a date is a new generation (D-490); `db/<date>.duckdb` is a link to the newest. An older one is there because a running job reads it: it goes at the next build of that date after the job ends. Never delete one by hand while a hold names it. A job that says "the lake generation this job was reading is gone" was started again after its generation was removed: send the request again |
| A job fails with `LAKE-STALE` "dated after today", or a night is refused as "dated after today" | the job's error or the adapter's log; `cat <lake>/CURRENT`; the box's clock (`date`) | a night is never ingested, accepted or pinned under a date after the site's today (D-529). **Refused at ingest:** nothing was written; check the date given to the run and the box's clock, then run the night again. **The served night itself is dated after today** (it was published before this rule, or while the clock was ahead): no later night can be served over it, and no list is built from it. Correct the clock first. There is no command yet that takes one served night back: restore the box from the last backup made before that night (runbook 05), then let the nights since run again |
| A night ends "failed" with `publish` in its data-operations row (for example `fhir: failed`) | the row's detail on `/data-ops` (`publish`: each step's state); `publish.json` in the night's folder; the audit event `ingest.failed` | the night passed the gate and its publish stopped at that step (D-489): the lake's build (judged, not served), OMOP, the FHIR store, the promotion, the pid map last. Nothing after the failed step ran, `CURRENT` still names the previous night, and the FHIR store was put back to that night (`fhir-store put-back failed` in the errors means it could not be: bring the FHIR store back, then run the night again). `stale`: a newer night is already served, so this one is not published. Fix the step's service and run the night again (the administrator's retry): the steps already done for the same data are not done again |
| A steward's accept of a held night answers "the publish ended failed" or "busy" | `publish.json` in the held night's folder; the adapter's log | accept publishes the held night through the adapter with the same steps (D-489). A failed step leaves the night held; a second accept goes on from that step. "busy": a running job reads the snapshot the night would replace; accept again when the job has ended. "stale": a newer night is already served; reject this one. If the page says the publishing was started and its end is not known, accept the night again: the accept is recorded (`dataops.decide`, `phase: started`), the night can no longer be rejected, and the second accept finishes the publish or records that it had ended |
| A night or a site publish says a snapshot "is being read by a running job" | the job list (running and awaiting approval); `ls <lake>/holds/` | a job holds the snapshot it reads (D-403): it is not rebuilt or pruned under the job. A site publish waits and goes after the job by itself; a held nightly re-run is run again when the job ends. A hold whose job is gone expires after 14 days; to free it earlier, end or cancel the job |
| A night or a site publish says a snapshot "is already building" | the lake's log; `ls <lake>/db/*.building` | another rebuild of the same snapshot runs (D-462); only one runs at a time. Wait for it: a site publish goes again by itself on the next tick; a night that ended "lake busy" is run again (nothing was written). A rebuild that was killed leaves nothing locked (the lock ends with its process) |
| A micro-batch summary says "Night budget reached" | the audit event `microbatch.budget` (re-checks, new patients and excluded patients carried over) | the night's micro-batch jobs, every study together, evaluate at most `TB_MICROBATCH_NIGHT_BUDGET` patients (default 2000, 0 = no limit; D-397). Each study's job reserves an equal share of what is left, so no study goes without because of its place in the order (D-458). Of a weekly job's share, `TB_MICROBATCH_EXCLUDED_PERCENT` (default 25) is kept for screening its excluded patients again, as far as there are any in scope (D-646); the summary says how many weekly runs a full pass over them takes. The rest wait for the next run, nearest visit first. With two or more job workers the first takes only the ingest, so long jobs never hold the night's ingest back (D-458). Raise the budget when the box finishes its nights early; lower it when the night jobs run into the morning |
| Containers lost egress after a restart | `deploy/network.sh status`; `systemctl status trialbox trialbox-egress-refresh.timer` | `deploy/network.sh apply` (the refresh timer does it within two minutes, D-377) |
| Docker does not start after a reboot; `trialbox-egress` failed | `journalctl -u trialbox-egress` (no or bad state file) | `systemctl disable trialbox-egress`, `systemctl start docker`, `deploy/network.sh apply` (writes the state file), `systemctl enable trialbox-egress` |
| `CERTIFICATE_VERIFY_FAILED` | hospital TLS inspection | put the hospital CA on the host, set `TB_EXTRA_CA=/abs/path/ca.pem` in `deploy/.env`, `docker compose up -d` |
| Many patients "need information" with "a result is in a unit that cannot be compared" | the lab's unit in the feed against the criterion's unit (`mapping_check.py`; `unit_defaults` in the site mapping) | declare the site's unit for that analyte, or ask the vendor for a tested factor (D-275); the patients are never excluded for it |
| Many orders or results read as unknown after an ingest | `mapping_check.py` lists status codes outside the map; the lake's `medication.status` = `unknown` | the HIS sends a status code the site mapping does not know: add it to the `status` / `result_status` map (an unknown code never counts as given or as final; D-275) |
| Many patients "need information" with "a medicine order has no end date" | the feed's order rows: no end date, or no date at all | map the order's end (or days of supply) in the site mapping (D-275) |
| Notes never exclude | `selftest.failed` in the audit, the admin health tile | the pair canary failed: check the models (§8, §10) |
| Notes never exclude; the run says "the verifier is not a second model" | `llm.pair.same_model` in the audit, `trialbox doctor` (`note_block` FAIL) | the verifier is the judge again (the same model name, alias, build or weights), or its endpoint does not say which weights it serves (`/models`). A note answer needs two different models (D-276): name a different verifier (`TB_GATEWAY_VERIFIER_MODEL`, or `LLM_VERIFIER_BASE_URL` with its own `LLM_VERIFIER_MODEL`), or set `TB_NOTE_BLOCK=never` on purpose |
| A screening run fails "the model did not answer"; rows say "not checked (system busy)" | the gateway log (`upstream_down` on a judge call: the server errors or drops the connection, and a batch job waits for it; `upstream_failed`: a 400 or 404 of the server, or a timeout, never sent again), `llm.gateway.call` with `fallbacks` | the judge's server is down or erroring. A judge call is never answered by the verifier build instead (D-276, LLM-002): bring the judge back, then send the request again |
| A SCREEN fails "the judge model did not answer 5 calls in a row"; later SCREENs fail at once | the gateway log, `docker compose ps` (the model service may be up but not answering) | the SCREEN breaker opened (D-389): it stops a run on a hung model instead of waiting up to 600 s a patient. Fix the model service; after `TB_SCREEN_BREAKER_WINDOW_S` (300 s) the next SCREEN tries one call and runs if it is answered. `TB_SCREEN_BREAKER_FAILURES=0` turns it off |
| A job seems to stand still while a model is down; later it goes on, or fails "the judge model did not answer ... its whole allowance" | `llm.outage` in the audit (which model, the refusal, seconds waited, resumed or gave up); the gateway log | a job waits for a model that does not answer and sends the same call again (D-456): an outage costs its own length and no patient goes to review for it. One job waits at most `TB_LLM_OUTAGE_WAIT_S` seconds in total (default 1,800), then fails. Fix the model service and send the request again |
| A job fails "interrupted by a restart of the box N times" | `job.requeued` in the audit (`restarts`), `docker compose ps` (restart counts), the kernel log for an out-of-memory kill | the orchestrator restarted more than `TB_JOB_MAX_RESTARTS` times (default 3) while this job ran, so the job was not started a further time (D-456): the job may be what stops the box. Find the cause of the restarts first. A job that is started again after a restart keeps the answers its models already gave |
| A SCREEN runs on after Cancel | the job's state | Cancel now stops a running job before its next model call (D-389): the job ends `failed` with step `cancelled`. Pressing Cancel again changes nothing |
| A tool imports the wrong code | the venv has another checkout installed | set `PYTHONPATH=libs:services:.` (the Makefile does) |
| Test ports taken | | `TB_HOST_<NAME>_PORT` in `deploy/.env` |

A failed job names its step (received, parsing, compiling, running, reporting) and the requester gets a plain
"Failed" mail.
