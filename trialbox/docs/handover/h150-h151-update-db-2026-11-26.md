## 1. H-150: the names on the network

**What the bench saw.** After `db-up: database: made again: it held another release's scripts`, the final
`docker compose up -d` failed: the orchestrator could not resolve `db`, and `docker inspect` showed no alias for the
database on trialbox-net (a fresh install of the same bundle: `[trialbox-db-1, db]`).

**The cause** (H150-01). No raw engine call recreates the container: every recreate of the update was already a
compose call for the box's project directory. H-137 (`deploy/docker-compose.identity.yml`, from fd3ee979) gave
trialbox-net an address range (`ipam`). For compose a network whose settings changed is made again, but only when
every container on it is in the command's selection. db-up's `up db` therefore only warns ("still used by
orchestrator ... not recreated"); the release's final `up` of the whole project removes the network, makes it again
with the new range and reconnects every container that was on it, without its service's name (`[]`). Reproduced on a
local engine (compose 5.7.1, engine 29.9.3) with a two-service project: db and orchestrator both `[]` after the final
`up`; `up -d --force-recreate` gives the names back. The update from 440089e8 passed because 440089e8 had no H-137.

**What changed.** `db_on_new_settings` (the database step of `db-up`, which the release being installed runs before
anything starts) now first calls `keep_names`: the box's own compose (`--project-directory` the deploy folder, so the
project and files of `deploy/.env`) runs `up --no-start --no-recreate --pull <setting>`, which puts every network on
the release's settings without starting or recreating anything; then `docker inspect` of every container of the
project (`compose ps -a -q`) is read, and each service whose container lacks its name on one of its networks (the
engine's own `host`, `none` and `bridge` left out) is recreated by the same compose: `up --no-start --no-deps
--force-recreate <services>`. A service still without its name stops the step, naming it and the network. The step's
line says which services were recreated. Shown on the local engine: forward, every name kept and the database
started after its recreate. A box without the installer's database step is left alone, as before.

**Not fixed by this card** (H150-02, a follow-up for the integrator to schedule: "a rollback to a pre-H-137 release
without an operator"). A rollback to a release from before H-137 runs that release's code and files: the network is
made again with its old settings and the names are lost again; nothing in a newer release can stop that. Runbook page
05 gives the recovery with shipped commands (`docker compose --project-directory deploy up -d --force-recreate`, then
the rollback again). The way to avoid it, option (a) of the lead's ruling: keep trialbox-net's settings as they were
and give Caddy's fixed range to a network of its own; Caddy would then have to leave trialbox-net
(`reverse_proxy console:8090` is pinned by `tests/console/test_identity.py`, and on two shared networks the name could
resolve to an address the console does not trust), and the console and Authelia join the new network. The lead ruled
(b) for this PR: H-137's network stays as it is.

**A test box beside a box.** The converge of a test box is that box's own compose (its deploy folder, so its `.env`
and its range from `testbox.nets`); the updater passes no setting of its own. Shown on the local engine: a test box's
converge left its network on its own range and the box's network (the same id) untouched.

## 2. H-151: the rollback's restore

**The cause** (H151-01). `RESTORE_SH` ran `pg_restore --clean --if-exists` over the database in place, after
`RESET_SQL` dropped what the restoring role and the database's owner own. The lake's schemas are owned by a group,
so they stay, and `--clean` drops the key of each partition child, which PostgreSQL refuses: "cannot drop inherited
constraint visit_occurrence_ydefault_pkey of relation visit_occurrence_ydefault", exit 3. Reproduced exactly on the
local test cluster with omop's migration 4 for one table.

**Found on the way** (H151-02). The old restore also fails on any database holding an extension the restoring role
does not own: `--clean` drops the extension ("must be owner of extension"). `trialbox_wf` holds `vector` and
`pgroonga`, made by the image's superuser (`deploy/docker/db-init/20-extensions.sh`), and is restored as `trialbox`.
Shown with the old script on the local cluster (pg_trgm standing in).

**What changed.** The dump is written whole to the 0600 script as before (a cut-off dump never reaches psql), then:
the superuser (the db container's `POSTGRES_USER`; the role itself when none is named) drops a fresh or replaced
database a killed run left (`<db>_tbrb`, `<db>_tbold`) and makes `<db>_tbrb` from template0 with the owner, encoding,
collation, ctype, connection limit and grants of the database in place; it makes the dump's extensions there (which
also gives each its comment). The role loads RESET_SQL and the script, without `--clean` and without the
`COMMENT ON EXTENSION` lines it may not run, in one transaction. Only then are the names swapped, in one transaction
(other sessions on the two databases ended first; the services are stopped by then), and the replaced database is
dropped (if that drop fails the restore stands and the next rollback drops it). Until the swap the database in place
is untouched: a failure, or SIGTERM, SIGINT or SIGHUP (the script's traps), drops the fresh database on the way out
and removes the script and its folder; the update keeps its marker, so the rollback can run again. The objects come
back owned by the restoring role (the dump is taken `--no-owner`), as they did after `--clean`; the role script of the
restart gives each schema and table back to its group. Database-level settings (`ALTER DATABASE ... SET`) are not
carried: the product sets none. `space_needs` counts the fresh database on Docker's volumes (H151-04).

**Not fixed by this card** (H151-03). The rollback runs in the process of the release installed before the update
(`apply_update.sh` runs `python3 -m tools.trialbox update` from the box's own tree, and `apply_update.sh rollback`
runs after the old tree is back). A box on c3a5b2b2 or 440089e8 therefore still rolls back with `--clean` and still
fails on a partitioned lake, and no shipped command of those releases completes that rollback: it fails again the
same way, `trialbox restore` of the update's own backup puts the data back (it drops every schema first) but leaves
the marker, and nothing shipped removes the marker. Runbook page 05 says so (keep the marker, restore from the
backup, call the vendor). The fixed restore proves itself on a box in an update from a release that carries it (the
candidate to a later bundle, then a forced rollback), and on the local test cluster.

## 3. Tests

- `tests/unit/test_update_network_alias_h150.py`: on inspect answers recorded on the local engine, the recreate goes
  through the box's compose (its project directory), after the networks converge and before the database starts, and
  no container or network is made by a raw engine call; a box whose names are kept is left as it was; a service still
  without its name stops the step; the engine's own networks are never read as lost; a test box's converge is its own
  compose with its own range. Failing first: the first 4 failed before the change (the test box's was added after).
- `tests/unit/test_rollback_restore_h151.py`, under dash on the session's test cluster, the restoring role an owner
  that is not a superuser and a member of the lake schema's group: a lake with a default and a year partition (key
  added on the parent), rows, a foreign key, a trigram index and grants comes back with rows, constraints, indexes,
  partitions, grants, extensions and the database's owner, encoding and grants equal; what the failed release made is
  gone and no second database is left. A cut dump and a load that fails half way leave the database as it was. A
  SIGTERM and a SIGHUP while the dump loads leave the database as it was and no second database. The space check
  counts the fresh database. Failing first: the three restore tests failed with exit 3 and the bench's message.
