## 2. The doctor on the box's host (line 1)

The doctor was run on a stand-in of an installed box: a deploy folder made as `deploy/install.sh` makes it, run on the
host's side as the runbook types it. Each WARN or FAIL row was read for its cause. Most were the stand-in's own state:
no engine, no NTP, no pins. Five rows were wrong on every installed box, whatever its state:

- `site_key` and `key_custody` read the secrets folder at the containers' path (`/run/secrets/trialbox`). On the host
  that folder is not there, so both said "not here".
- `key_ceremony` read the same folder. Finding nothing there, it passed with "no KEK yet" without looking.
- `flags`, `provenance_index` and the pid-map half of `site_key` connected to `TB_DB_URL`. That address names the
  host `db`, which only the compose network resolves, so each said the database "did not answer".

Now, on the box's host (not in its image, with a `deploy/.env` there):
- the secrets and lake volumes are read where the engine keeps them (`TB_SECRETS_HOST_DIR`, else
  `TB_DOCKER_VOLUMES` with the project's `tb-secrets` and `lake-data`, as `audit_heads.host_dirs` reads them);
- the database is read through the box, `compose exec -T db psql`, read-only (`box_hold.query`, which H-136's hold
  reading now shares);
- `provenance_index` runs `trialbox provenance --check` in the box's orchestrator (`box_hold.run_in`).

A box that does not answer is a WARN that names the cause, never a pass. A pid map holding another key is still a FAIL.
The test reads the whole run and holds every row to one rule: no row names a container's place. It lists no rows.

Not changed: the M1 rows "Information still needed", `memory_caps` and `audit_heads` on a new box. They are true open
items, not false reds.

## 3. Go-live and key escrow (line 4, R22-33)

`tools/key_escrow.go_live` decides, and it fails closed. Each of these is a refusal, and each says why:
- the secrets folder is not here, or cannot be read;
- there is no KEK;
- the KEK is TPM-sealed (back end `file`) and has no escrow set;
- the set is of an older KEK;
- there is no ceremony record of the current KEK;
- the newest record does not list the set.

A KEK that is not bound to the board passes, and the reason names its back end.

The acceptance has the new criterion `key_escrow`: `tools/acceptance.py key-escrow --secrets <folder> --deploy
deploy` (RUNBOOK §6, step 10). `report` says NOT YET until it has passed, as it does for every criterion not run.

The doctor's row `key_escrow` comes through F0's hook (`doctor_m5.doctor_checks`). On a VALIDATION or PRODUCTION box
it is a WARN that names `[go-live gate key-escrow: open]`. It is a WARN, never a FAIL, so a box installed before its
key ceremony stays green. A DEV or TEST box gets no row. M4's anchor gate is written the same way.

The record step (`key_ceremony._escrow`) still makes a TPM record without escrow. The order of the ceremony and the
escrow is the SOP's to say. The gate is at go-live (INTM5-04).

## 4. The backup's audit queue (line 5, PR1305-H6)

`ComposeOps.audit` holds `deploy/site/backup-audit.lock` (`flock`) for its whole read, send and write. This is its own
lock file, so a caller already inside `backup.lock` never waits on itself.

The queue with the new event is written whole (write-then-rename, fsync) before anything is sent. Before this change, a
new event lived only in memory while the older ones were sent. A signal partway through lost it (INTM5-03, found while
writing the test). Now a signal can at worst send an event twice; it never drops one.

H-142's kill -9 and full-disk tests pass unchanged. On a full disk the first write is skipped and the sends still go.

## 5. A rerun of the same restore takes off its own hold (ruling 7178128292)

`tools/trialbox/backup.py` writes the restore's id first in the hold's reason: `[restore <backup sha256>@<run start,
UTC>]` (`restore_id`). Before the trial database is replaced, `own_rerun_hold` reads the flag's latest event.

The hold is this restore's own, so not "carried", only when all three of these are true:
- the latest event sets `held`;
- its actor is the restore's;
- its reason starts with an id whose backup is the one being restored.

Then the usual release of a complete restore takes the hold off. Its reason names both restore ids and the backup's
sha256, and `backup.restored` carries `restore_id` and `rerun_of`. An earlier restore's set-aside audit chain still
makes the hold carried.

There are five tests, each failing on the base (`tests/unit/test_restore_rerun_releases_own_hold_m5.py`):
- one per condition: the same backup, the id on the hold, nothing changed since, and complete. Each has its positive
  control.
- one that sends TERM, KILL and a power loss (`killpg` SIGKILL) for real to a restore in a child process, at the same
  step. All three reruns release the hold.

The changed assertion, ruled by the integrator before the push (7179262165): `test_restore_hold.py::
test_a_restore_that_stops_after_the_database_was_replaced_leaves_the_box_held`. Its rerun now releases the hold.

"Every service healthy" is not a condition of the release. The release happens inside the restore before the services
start, as every complete restore's release does today. The health check is the host step's exit code (H-126).
RUNBOOK §5 says so at the end of its restore section.

## 6. The review's fix batch (7181403737, section 1534: four Mediums)

Each fix has a failing-first test named `test_review_1534_*`, with fixed clocks:

1. **A long mismatch stayed a WARN.** `box_hold.run_in` cut the box's answer to its tail, so a "differs from the
   chain" header followed by many rows was lost. It now keeps the whole answer. The doctor judges by the exit code
   and the first line: exit 1 is a FAIL unless the first line says the index is not installed. The test has 20
   differing rows.
2. **The send had no limit.** Each send under `backup-audit.lock` now has `query_timeout`
   (`TB_BACKUP_QUERY_TIMEOUT_S`). A hung send keeps its event and gives the lock back.
3. **A wrong secrets path passed.** On a VALIDATION or PRODUCTION box, a secrets folder that is not there is now a
   WARN for `key_ceremony`, never "no KEK yet".
4. **A carried hold could be taken for the restore's own.** A hold the restore keeps as carried (a person's, or
   another restore's) is now written `[restore <id> carried]`, and `own_rerun_hold` refuses it. The test runs two
   restores of a person-held box, with the set-aside audit chain removed between them.
