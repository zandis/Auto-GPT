## 1. Verdict

TrialBox is **not fit yet to hold real patient data in a hospital, but it is close on architecture and far on platform**. The security design (TB-DS-03) is above average for a product at this stage: data classes enforced in code, pseudonymisation at ingest, an egress allowlist, a hash-chained audit, signed offline updates, a two-model rule, and a threat model that already uses STRIDE and the OWASP LLM Top 10. The regulatory position (non-device research-operations tool) is defensible in both countries if the wording and feature boundary in TB-DS-16 §4 hold.

Three things undermine it today:

1. **The platform moved and the hardening did not.** D-125 puts the box on Windows 11 / WSL2. Every hardening control in `docs/HARDENING.md` (LUKS2, TPM-sealed keys via `systemd-creds`, swap off, nftables from a systemd unit) and `deploy/check_host.sh` assumes Ubuntu Server on bare metal. On WSL2 there is no TPM device, no LUKS, a hidden swap VHDX by default, and any Windows user with a logon on the box gets Linux root with `wsl -u root`. The key custody story (TB-DS-03 §6) is therefore not implemented on the platform the hospitals will receive. **[V] for the mismatch, [I] for WSL2 behaviour on the real box.**
2. **The service boundary is "one shared secret in every container".** `TB_SERVICE_TOKEN`, the mail passwords, the Postgres password and `CLOUD_LLM_API_KEY` are in `deploy/.env`, and `env_file: [.env]` hands that file to every Python service (`deploy/docker-compose.yml:19`). A compromise of the least trusted container (doc-parser reading a hostile PDF) yields the token that unlocks `/jobs/{id}/reveal`, which resolves **any** pid in the hospital's pid map under **any** actor name the caller writes into `X-TB-Actor`. **[V]**
3. **Production install path is broken for the console** and there is no MFA, no backup, no TLS termination and no OIDC/SAML in the product; these are all marked "H" (hospital stage) in the design, which is allowed by the owner's rule, but MHLW GL 7.0 2FA, APPI/PDPA security measures and every hospital questionnaire will require them on day one of real data, so they must be **built now** even if switched on later. `deploy/install.sh:178-184` runs `exec console` against a compose set that has no `console` service (`deploy/docker-compose.yml` lists db, fhir-store, lake, embed-service, doc-parser, criteria-compiler, adapter, orchestrator, mail-gateway, gateway, llm-stub, llm-service; the console exists only in `docker-compose.poc.yml`). **[V]**

The SaMD position is sound; the PPAP-style password-zip mail (`services/mail_gateway/outbound.py:196-210`) is a cultural and policy misfit in Japan and should be removed before a Japanese site sees it.

Score as a reviewer: design 4/5, build 3/5 for the Linux appliance, **2/5 for the Windows/WSL2 appliance the owner just chose**.

## 3. Is TrialBox a medical device / SaMD?

**Position: not a medical device in Japan (プログラム医療機器) or Taiwan (醫療器材軟體), as long as intended use and features stay as TB-DS-16 states.** I agree with TB-DS-16 §1-5 and add the following.

**Japan [V on the guideline; position is reasoned, not a listed exemption].** The 2021/2023 該当性ガイドライン asks (1) is the program intended for diagnosis, treatment or prevention, and (2) could a malfunction affect life or health. TrialBox counts and lists candidates for *research operations*; the investigator decides eligibility under the protocol. The guideline's non-device examples (hospital administration programs; patient explanation programs) are close relatives. The things that would pull it in are exactly XL-01..07 in TB-DS-16 §4; I add:
- **XL-08**: showing a criterion verdict with clinical wording that reads as a finding about the patient's condition ("patient has CKD stage 4") outside a research frame. Keep the on-screen wording "criterion X: supported by note dated Y" and keep the no-score rule (TB-DS-11 H-02(g)).
- **XL-09**: AE *grading* by the model (CTCAE grade suggestions) presented to a clinician. Suggesting "a note mentions an event; investigator to review" is research-record support; computing a grade for care decisions edges toward diagnosis. Keep grading human.
- **XL-10**: any patient-facing surface (the later phone app must stay staff-only; the consent explainer page is a reading aid, not interactive advice).
- The 2018 clinical-research-use notice is not a route TrialBox should rely on (TB-DS-16 §3.2 is right).
- Wording to use everywhere (UI footer, PDFs, mail, sales): the TB-DS-16 §2 statement. Add 「本ソフトウェアは医療機器ではありません」/「本軟體非醫療器材」 to the footer. Avoid 「診断支援」「AIが判定」「見逃し防止」.
- Recommendation: request a written 該当性 consultation (MHLW 監視指導・麻薬対策課 / PMDA) **before selling to pharma**, not before the academic pilot. Fee and route: confirm with counsel (RP-03).

**Taiwan [V on the law and the 2022 guideline].** 醫療器材管理法 Art. 3 defines devices by intended use. TFDA's 醫用軟體分類分級參考指引 (111.9.15) separates 醫用軟體 (any software handling health records) from 醫療器材軟體 (those meeting Art. 3). Record-management and research-support software is 醫用軟體 but not a device unless it claims diagnosis/treatment. Same boundary as Japan. Recommend: a written inquiry to TFDA only if CGMH's research office or a sponsor asks (RP-02). Note that TFDA has published separate AI/ML SaMD guidance for devices; it does not apply while non-device.

**What changes the answer (both countries):** the trial-conduct features planned for later (AE suggestions, visit-window alerts) must be framed as *investigator tasks for GCP duties*, never as *clinical alerts*. Writing to the EMR is excluded by owner decision 2 (good). The outside-access apps must not deliver alerts about a patient's clinical state to a clinician's phone.

**Design choices that keep it outside (checklist for every PR):** no diagnosis/stage/risk score; no treatment suggestion; no clinical alert; no imaging/signal processing; no EMR write; no patient-facing clinical content; wording reviewed against TB-DS-16 §2 (add this to `tools/public_walk.js` as a forbidden-word list: 診断, 判定, 対象外, 不符合, 建議治療).
