# TrialBox independent review: design and code (master `019770e`, plan v4)

Reviewer: Claude (Fable), adversarial pass, 2026-11-08. Judged against the owner's standing decisions (standalone, own Postgres tables for CRF answers, SQL-only runtime engine, v1 lifecycle scope, the three hardware profiles, the Gemma/Qwen pair, three languages, Windows/WSL2 delivery, apps-after-platform with a token-protected API for every screen action, no development gates).

What I ran myself: `tools.e2e_simple` 48/48 PASS in 65.8 s; the role demo served on 127.0.0.1:8097 and walked with Playwright as PI and CRC in ja and zh-TW on a 1280 px desktop and a 390 px phone (screenshots in `scratchpad/shots/`, machine report in `shots/report.json`); one experiment on the audit chain (a torn last line). Everything marked **[inferred]** was read, not executed.

## 1. Verdict

The screening core is sound and tested: filters first, unknown is kept, a note answer excludes only when two models agree on a verified quote, the canary gates exclusions, one judge path, coded reasons, pages in three languages. The build around it is not yet a platform: the clinical console only exists as a DEV/TEST "pilot workspace" that refuses to start on real data; mail delivery is not idempotent (a restart re-sends patient lists); trial facts live in five SQLite files with no backup; the audit chain bricks the box after one torn line; and nothing a PI or CRC does on a page has a token-protected API, which D-125 now requires. Plan v4's order (data core → importers → forms → lifecycle) is right, but step 2 is under-scoped (it says "move SQLite to Postgres and back up"; it must also fix delivery idempotency, the audit repair path, the production console and the env-default inconsistencies) and nothing in steps 2–5 produces the API the apps need.

Overall **3.0 / 5** for "platform readiness"; the screening engine alone would score 4.
