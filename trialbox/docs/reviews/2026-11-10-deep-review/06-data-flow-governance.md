## 1. Summary

The happy path works and is well checked. `e2e-simple` passes all 19 stages; idempotent re-ingest is byte-identical; the
OMOP store keeps before-images, tombstones, provenance and refuses an older batch; the backup is encrypted, hashed and
restores row-for-row into a fresh cluster in under 5 s on 520,745 rows; no chart number, name, ID number or phone was
found in any log, audit line, mail or export file the e2e run wrote.

The weak side is **what happens when the hospital feed is wrong**. The box's ingest has no completeness gate: a missing
or empty table passes, becomes the served snapshot and, after three such nights, prunes every good snapshot. The
project already has a data platform (`services/dataplat`) that holds exactly these feeds (`TABLE_MISSING`,
`VOLUME_ZERO`), but the box does not run it. Identity is fragile too: a lost site key or a zero-padded chart number
silently gives patients new pseudonyms, and the opt-out does not follow.

Counts (new findings): **Critical 1, High 5, Medium 10, Low 3** (19). Registered rows reproduced by a run: 6.

Top 5:

1. **DATA-001 (Critical)** No completeness gate: `lab.csv` missing → 2,837 lab rows gone, `patient.csv` empty → 0
   patients, `medication.csv` missing → GZQO FEAS 13 → 0; every night "passed", `CURRENT` moved, good snapshots pruned.
2. **DATA-002 (High)** Two ingest stacks: the governed one (`dataplat`: contracts, quarantine, publish gate, MPI with
   merges, lineage) is test-only; the box runs `adapter`, which has none of it, and the two derive different pseudonyms.
3. **DATA-004 (High)** A missing site key is silently re-created: every pseudonym changes, ingest passes, and an
   opted-out patient is back in the lake as a new, not-opted-out patient.
4. **DATA-006 (High)** Consortium COHORT tables leave the box with primary suppression only; nested counts and
   quarters allow differencing. FEAS already uses controlled rounding; COHORT does not.
5. **DATA-003 (High)** The HIS CSV reader is UTF-8 only: a Big5 or Shift_JIS export crashes the night with no report and
   no audit event. PR #70's encoding detector does not cover this reader.

## 4. What is good (keep it)

* Idempotency: the same feed gives byte-identical NDJSON (sha `c4cdef06…` three times), the OMOP re-load writes nothing
  (19,532 `same`), the derived batch writes nothing (1,600 unchanged), FEAS and SCREEN re-runs are byte-identical.
* OMOP loader design: one transaction under an advisory lock, before-images for every update and tombstone, restore
  with the same id, refusal of an older batch, provenance per record. This is the model the legacy path should follow.
* Pseudonymisation at the door: no chart number, name, ID number or phone in any lake column, audit line, mail, export
  or log the e2e run wrote (0 hits over 5,000 synthetic patients). Mail shows pseudonym + screening number only.
* Proposed facts never count (e2e stage 12; OMOP loads them with their type concept; the lake keeps them in
  `site_fact`). Absent diagnosis or medicine in EDC prefill is unknown, never "No".
* The held-night mechanism, the export ledger (`flow.export`), the encrypted backup format (X25519 + AES-GCM, chunk
  authentication, sidecar hashes), the restore-and-compare drill and the PITR check.
* `dataplat`'s contracts and publish gate: they caught both bad feeds. Port them, do not rewrite them.

## 6. Questions only the owner can decide

1. **Which ingest stack is the product?** `adapter` (runs on the box) or `dataplat` (governed, test-only). Recommended:
   keep `adapter` and its pseudonym rule; port `dataplat`'s contracts, publish gate and MPI merges into it before
   CGMH go-live; avoid any change that re-keys pseudonyms after the first real ingest.
2. **Erasure and the audit chain.** May an erased patient's pseudonym stay in the 10-year audit? Recommended: yes, as a
   documented legal basis (audit of research access), with every other store erased; revisit with each site's privacy
   office. If a site says no, switch to per-patient tokens (DATA-013).
3. **Consortium counts.** Apply the same disclosure control to COHORT as to FEAS (k = 5, rounding base 5, differencing
   check)? Recommended: yes; a contract may only tighten it.
4. **National ID storage.** Keep name + national ID for every patient for TWPAS? Recommended: no; take it only when a
   TWPAS case is opened.
5. **Delta nights.** Recommended: full nightly exports with the completeness gate at both pilots; allow deltas only
   with a change-timestamp column.

## 7. Assumptions

* The demo mapping (`tw_core/demo_his.yaml`) and the fixture represent the shape of a CGMH-type CSV export; the real
  export's encoding and table list are unknown until the site survey.
* "Default nightly" means the scheduler's INGEST job without `since` (as in `scenarios/admin.py:58`).
* The legacy lake is what the pilots serve until `lake.source` flips (CR-060); OMOP findings apply after the flip.
* Severity of DATA-001 is Critical, not Blocker, because a person reviews every candidate before contact; it would be
  a Blocker if lists were sent without review.
* RTO and RPO figures are from synthetic data on a shared 4-core machine; a real box with full history will be slower.
